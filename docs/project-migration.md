# 项目迁移与工作流改绑

项目换了目录、或整个搬到另一台机器之后，原来跟踪的会话会「找不到、写不进」。本文说明原因，以及怎样用 `relaymesh rebind-workflow` 让会话跟着项目一起走。

## 为什么会丢

- 会话按「**主机名 + 项目目录**」隔离：`list_sessions` 与 `workflow_context(action: list_workflows)` 默认只列出当前主机、当前项目目录下的会话。
- 主机名不是模型自己报的，而是取自**所用 MCP 凭据登记的主机名**，防止伪装。
- 一个 `workflow_id` 一旦绑定了某个项目目录，换另一个目录再往里写，会被项目隔离（D-161）拒绝：「该工作流已被项目 … 占用」。

所以项目搬到新目录 / 新机器、用新机器上的凭据继续工作时，旧工作流既列不出来，也写不进去；不带 `workflow_id` 时则会另起一个全新的工作流，旧的就被留在原地。

## 迁移步骤

1. 先把项目内容搬到新位置（`git clone`、`rsync` 等），并在新机器上配置好它自己的 MCP 凭据。
2. **看现状**（只读）：

   ```bash
   ./relaymesh rebind-workflow --list
   # Docker 部署：
   docker exec relaymesh /app/relaymesh rebind-workflow --list
   ```

   会列出每个工作流当前绑定的目录与主机，以及各凭据登记的主机名（不含令牌）。`--to-host` 应与**新机器所用凭据登记的主机名**一致。
3. **预演**（默认就是预演，不写任何数据）：

   ```bash
   ./relaymesh rebind-workflow --workflow <工作流 ID> --to-dir <新项目目录的绝对路径> --to-host <新主机名>
   ```

4. 确认无误后加上 `--apply` 执行。
5. 回到新位置继续。此后用新凭据、在新目录里调用，既能列出旧会话，也能继续同一个工作流；不带 `workflow_id` 时会按项目目录自动继承它。

## 安全与回滚

- 默认只预演；`--apply` 之前一定先在数据库同目录生成快照 `<db>.rebind-<工作流>-<时间>.bak`。
- 单个事务内完成，提交前校验结果（目录唯一、主机符合预期、行数不变），任何一项不符就整体回滚。
- 只改这个工作流名下**会话与排队反馈**的目录 / 主机；不动正文、不动更新时间（不会让它看起来刚刚活跃）、不动凭据绑定、不动其他工作流。
- 回滚有两种：
  - 原路改回：命令执行完会打印现成的反向命令（把目录 / 主机改回原值）；
  - 整体恢复：停止服务，删除 `<db>-wal` 与 `<db>-shm`，再用快照覆盖主库文件。
- 它**刻意不是 MCP 工具**：改绑会绕开跨项目隔离，所以只开放给能访问数据库的运维人员。

## 注意

- 改绑之后，仍在旧目录里运行的 AI 再写入这个工作流会被隔离拒绝，需要在新位置继续。工作流里还有等待回复的会话时，命令会提示。
- 同一个工作流同一时间只应绑定在一个位置；要在两处各自独立工作，请使用各自的 `workflow_id`。
- 目标主机名没有出现在任何凭据里时，命令会提醒：此时新位置按主机过滤会查不到。
