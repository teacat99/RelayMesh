# 追加指令收件箱

智能体在埋头干活的时候，并没有在「等你回复」。这段时间你在网页里补充的话，过去只会合并成一条，等智能体下一次发起交互时才被带走；你既不知道它有没有看到，它也可能一整段任务都没发现你说过话。

收件箱把这件事做成了有状态的流程：

- **每条追加单独入库**，有自己的状态：已排队 → Agent 已读取 → Agent 已确认；
- **智能体有三种办法在工作中途发现它**（下面叫「三层发现」），不必等到下一次交互；
- **网页上实时看得到每一条走到了哪一步**、是哪条路径被发现的，读了之后还能撤回并通知智能体；
- **每一层都有开关**，随时可以关。

## 一条追加的一生

智能体没有在等你回复时，输入框的发送按钮会变成 **追加指令**。点击后，这条追加会作为一个**永久的气泡**出现在对话里：头部写着「您的追加信息」和时间，紧跟一枚状态徽标；右侧是 hook 提取状态（经哪条路径读到、什么时候）和撤回按钮。

| 状态 | 气泡徽标 | 含义 |
|---|---|---|
| 已排队 | `待 AI 提取` | 已保存，智能体还没读 |
| Agent 已读取 | `AI 已读取` | 智能体调用了 `inbox` 读到了全文（右侧会写明经哪条路径发现的） |
| Agent 已确认 | `AI 已接收` | 智能体调用了 `inbox_ack`，或在下一次汇报（`interactive_feedback`）时被隐式确认 |
| 已撤回 / 已过期 | `已过期`（撤回的会从对话里撤走） | 你撤回了；或超过 7 天没被取走 |

要点：

- **撤回**：还没被读取的，点「撤回指令」，内容回到输入框重新编辑；已经被读取的，按钮是「撤回并通知 Agent」，内容同样回到输入框，智能体下次读取收件箱时会被明确告知「忽略这一条」，且只告知一次。
- **秒回**：智能体下一次发起 `interactive_feedback` 时，所有排队中的追加会按时间顺序合并成一次即时回复带走，已读取未确认的会被隐式确认，行为和过去一致。
- 同一个工作流里最多同时保留 100 条未确认的追加，防止误操作或脚本无限堆积。已确认、已过期的追加**一直留在对话里**，不会因为过了一天就消失；`get_session_history` 同样会带出它们（只读）。
- 工具栏里（执行状态块与阶段滑块之间）有一个**收件箱状态块**：文字是 `hook 刚刚` / `hook 未装` / `收件箱` / `提醒已关`，旁边的数字徽标是 `待提取 N`、`待确认 N`；点开能看到完整说明——「Agent 最近一次与 RelayMesh 交互」（用来判断智能体是真的还在干活、还是已经走了）、三层提醒各自的状态、hook 的状态与安装命令、各状态的数量。「最近一次交互」只放在内存里，服务重启后清空；hook 的「最近出现」则会按每分钟至多一次落库，重启后恢复，所以 `hook 刚刚` / `hook 未装` 不会因为重启（含热更新）而误判。

## 三层发现

三层各自独立、可单独关闭，覆盖的场景不同：

| 层 | 怎么工作 | 要不要安装 | 什么时候起作用 |
|---|---|---|---|
| **回执提示行** | 智能体调用任何带 `workflow_id` 的工具时，回执末尾多出一行 `inbox:`，写明有几条没读、最早一条多久以前、最新一条的开头 | 不需要 | 智能体下一次调用任何 RelayMesh 工具时 |
| **编辑器 hook** | Cursor 的 `postToolUse` hook 在每次工具调用之后问一下服务端，有未读就把提醒塞进智能体的上下文；`stop` hook 在智能体准备收尾时再拦一次 | 需要在项目里装一个脚本（见下） | 智能体调用**任何**工具之后——包括它根本不碰 RelayMesh 的时候 |
| **提示词条款** | MCP 握手时下发的使用说明里多一节：看到回执里的 `inbox:` 行要先读收件箱，并说明它的权限等同于你的正常反馈 | 不需要 | 让智能体「知道有这回事」，是前两层的基础 |

只用第一层和第三层就已经能用，hook 是更主动的补充：它不依赖智能体碰不碰 RelayMesh。

### 智能体侧的工具

三个动作都在 `workflow_context` 里，必填 `workflow_id`：

| action | 作用 |
|---|---|
| `inbox` | 返回还没读的追加的**全文与图片**，标记为已读取；同时列出读过但没确认的。`recent=true` 还会列出最近一天内确认过的（上下文被重置后有用）。没有新消息时只回一行，几乎不耗成本 |
| `inbox_ack` | 确认已经处理。`ids` 可以只确认指定的几条（追加编号，就是 `追加 #12` 里的 12），不填则确认所有已读的。可选：下一次汇报会隐式确认 |
| `inbox_peek` | 只读状态（数量、预览、距今多久），不改变任何状态。**给 hook 用的，智能体自己不需要调用** |

追加里带的图片，用 `get_session_image` 取，`session_id` 写成 `inbox-<编号>`，`inbox` 的回执里会给出完整的调用。

## 引用某条回复（回复哈希）

会话页里每条智能体回复——一轮汇报或一条进度通知——都有一个 8 位的短哈希，就是会话编号 `sess-` 之后的部分（`sess-9f02517c` 的哈希是 `9f02517c`）：

- 轮次头上有「引用」按钮，进度气泡上直接显示哈希（它本身就是引用按钮），恢复胶囊展开后有「引用此胶囊」；
- 确认卡（智能体的提问 / 计划确认 / 文档决策，**待答复的和已处理的都有**）右上角有「引用」按钮，引用的是确认项编号：`【确认 Q5】`（见 [confirm-items.md](confirm-items.md#已处理的卡回看与引用)）；
- 点一下，输入框光标处插入 `【回复 9f02517c】`（胶囊是 `【恢复 r8】`，确认项是 `【确认 Q5】`）。桌面端同时聚焦输入框，光标落在标记之后可以直接接着写；触屏设备不抢焦点（免得弹出软键盘）；同一个标记已经在文字里时不再重复插入。

用户的话交给智能体时——阻塞汇报的反馈、`inbox` 读到的追加、确认项答复里的备注——Hub 会在这段话后面附一块 `=== 引用 ===`，让智能体不必对着一串哈希猜：

- 回复：第几轮汇报 / 进度通知、标题、时间、`session_id`、开头约 120 字，以及用户当时对那一轮的回复开头；要读全文用 `get_session_history` 带 `session_id`；
- 胶囊：修订号、时间、状态与「目标」开头；要读全文用 `workflow_context(action: "checkpoint_get", revision: N)`；
- 确认项：类型（提问 / 计划确认 / 文档决策）、标题、时间、风险级别与状态（还在等用户答复 / 用户已答复 / 用户已忽略 / 已撤回 / 已过期），**全部选项（带推荐标记）、用户选了哪个、备注**与正文开头，形如 `【确认 Q5】提问「…」（10-15 17:20，风险 L1，用户已答复）；选项：a「…」、b「…」（推荐）；用户的答复：选 b「…」，备注「…」；正文开头：「…」`——用户事后引用一张已处理的卡，多半是要对着当时的方案与答复继续说下去，所以选项与答复比正文开头更要紧；要读全文用 `async_ask(action: "get", ref: "Q5")`。

边界：

- 只在**同一个工作流**里解析：别的工作流里哈希相同的会话不可见，它们的标题与内容不会被带出来；找不到（已删除、不属于本工作流）时如实写「没有找到」；
- 写法不合法的（哈希太短或不是十六进制，胶囊序号不是正整数，确认项编号不是 1~6 位正整数）当作普通文字，不算引用；确认项的 `Q` 可省略（`【确认 5】` 也认）；
- 一条消息最多展开 5 处，其余只提示「另有 N 处引用未展开」；6 位以上的前缀可能对上多条，按时间由早到晚列出（最多 3 条）；
- 引用是纯文字约定，不新增数据表，也不影响收件箱的状态流转。

## 手动开关

**设置 → 等待策略 →「追加指令收件箱 · 提醒智能体」** 里有一个总开关和三层各自的开关，每个开关点一下就保存并立即生效，默认全开。设置页会写明「当前生效」的是哪几种提醒方式。

| 开关 | 关掉之后 |
|---|---|
| 总开关 | 三层全部静音：回执里没有提示行、hook 查询不再提醒或拦截、提示词不再带条款。**已排队的追加不会丢**，智能体发起交互时照常带走 |
| 回执提示行 | 回执里不再有 `inbox:` 行 |
| 编辑器 hook | hook 来问时服务端一律回「没事」，也不会再拦截收尾。脚本不用卸载 |
| 提示词条款 | MCP 使用说明里不再有收件箱那一节（对新建立的 MCP 连接生效） |

工具栏的收件箱状态块会如实反映开关：全关时显示「提醒已关」，点开能看到是哪一层关着。

也可以从部署层面强制关闭：设置环境变量 `RELAYMESH_INBOX=off` 后，总开关被固定为关闭，界面会提示「由环境变量关闭」，也无法在界面里打开。

## 安装 Cursor hook

### 前提

- 本机有 `curl`（或 `wget`）与 `sha256sum` / `shasum`。`relaymesh-hook` 是 Go 编译的单个可执行文件：Hub 自带 `agent-dist` 目录时（Docker 镜像已内置）从 Hub 下载；没有时（单二进制、`go run`、stdio 直驱）安装脚本会自动改从 GitHub Release 下载，见下面的「下载来源与回退」。
- Cursor 的 `~/.cursor/mcp.json` 里有 RelayMesh 这一项，名字是 `relaymesh`（别的名字用 `--mcp-server` 指定）。hook 用它里面的地址和令牌（`Authorization` 请求头，或直接写在地址里的令牌）去问服务端，**不需要另外配置令牌**。

### 一条命令

在项目根目录执行（会话页工具栏的收件箱状态块点开后，点「怎么装？」可以直接复制到带有当前地址与工作流的这一条）：

```bash
curl -fsSL 'http://<服务地址>/hooks/cursor/install.sh' | RELAYMESH_HOOK_INSTALL_BASE='http://<服务地址>' sh -s -- --workflow '<智能体用的 workflow_id>'
```

`install.sh` 由 RelayMesh 服务提供（`/hooks/cursor/install.sh`，不需要登录，不含凭据）：识别系统与架构 → 下载 `relaymesh-hook-<os>-<arch>` → 校验 `checksums.txt` → 安装到 `${RELAYMESH_HOOK_DIR:-$HOME/.local/bin}` → 运行 `relaymesh-hook install`。Windows 用同目录下的 `install.ps1`，来源与校验规则相同。

> 如果你是通过**自签名的 HTTPS 地址**（例如 `https://<局域网 IP>:18776`）打开的网页，`curl` 会拒绝证书：下载脚本与二进制时改用 `http://<局域网 IP>:18775/...`，或给 `curl` 加 `-k`。

### 下载来源与回退

脚本按下面的顺序找 hook 程序：

1. 设置了 `RELAYMESH_DOWNLOAD_BASE`（自建镜像，其下要有同名二进制与 `checksums.txt`）→ 只用它，失败就报错，不会悄悄改去别处；
2. 本 Hub 的 `/hooks/cursor/bin/`：Docker 镜像和带 `agent-dist` 目录的部署都有；
3. Hub 下载不到（**单二进制、`go run`、stdio 直驱的部署没有 `agent-dist` 目录**；也可能是地址不可达或被限流）→ 自动改从 **GitHub Release** 下载：Hub 是正式版本（`vX.Y.Z`）时取**同一个版本**的 hook；开发版或版本未知则取最新 Release，并提醒两边版本可能不完全一致。

可调的环境变量：`RELAYMESH_VERSION`（例如 `v2.0.0`，或 `latest`）指定 Release 版本；`RELAYMESH_REPO` 换成自己的 Fork（默认 `teacat99/RelayMesh`）。

不论从哪里下载，都用**同一来源**的 `checksums.txt` 校验 SHA256：没有对应条目就拒绝安装，校验不通过也**不会换源重试**，更不会留下二进制。两处都下不到时，脚本会列出试过的地址，并给出手动安装的办法（自己下载二进制、`chmod +x`、再运行 `relaymesh-hook install --workflow ...`）。

> GitHub Release 要 **2.0.0 起**才附带 `relaymesh-hook-*`；更早的 Release 只有 Hub 本体，回退会失败并给出上面的手动办法。

### stdio 直驱下装 hook

stdio 直驱（`relaymesh mcp stdio`）也带着同一个 Web 控制台，页面上的一键命令照常可用，下载走上面的「回退」。区别在发现：stdio 条目在 `mcp.json` 里没有地址也没有令牌，hook 找不到去哪问、凭什么问，所以**一键命令装完后还要补两样东西**：

1. 给 RelayMesh 的 stdio 条目配一个环境令牌，让这台 Hub 的本机 HTTP 端点 `http://127.0.0.1:18775/mcp` 认它：在该条目的 `env` 里加 `"RELAYMESH_MCP_TOKEN": "<自己生成的一串随机字符>"`（令牌只写在 `mcp.json` 里，不要写进命令行、`hooks.json` 或 `relaymesh.json`）；
2. 让 hook 拿到同一个令牌与地址：启动 Cursor 的环境里设置 `RELAYMESH_TOKEN` 为同一串字符（hook 默认从这个环境变量读令牌；用桌面图标启动的 Cursor 看不到终端里的 `export`，要在系统层设置，或从终端启动 Cursor），并在一键命令末尾追加 `--mcp-url http://127.0.0.1:18775/mcp`。

这一步比较别扭，所以**不装 hook 也能用**：收件箱照常工作，只是靠回执末尾的 `inbox:` 提示行与提示词里的约定提醒智能体；异步模式需要 hook 的上报，会提示「hook 未装」并保持同步模式。stdio 条目的令牌 / 地址自动发现暂未提供。

**hooks.json 里的命令路径**：`install` 默认把 **本机二进制绝对路径** 写进 `.cursor/hooks.json`（项目根为工作目录、PATH 可能很精简、仓库常被多台机器共享）。若你更想用固定命令名，可 `relaymesh-hook install --command 'relaymesh-hook'`（前提是二进制已在 PATH 里）；`relaymesh-hook status` / `doctor` 会提示登记的路径在本机是否存在。

`relaymesh-hook install` 做了两件事，**改动前会先给你看、改动时会先备份**：

1. 在 `.cursor/hooks.json` 里登记十个 hook：收件箱用的 `postToolUse`（`post-tool-use`）与 `stop`（`stop`，`loop_limit: 1`），以及只用来上报 Agent 运行状态的八个（见下文「hook 汇报的运行情况」）。已有的其他 hook **原样保留**；若之前登记过 Python 版，会**迁移**为 Go 二进制；重复执行幂等；`hooks.json` 不是合法 JSON 时拒绝改写。
2. 写 `.cursor/relaymesh.json`，告诉 hook 这个项目对应哪个工作流（**不含令牌**）。

| 选项 | 作用 |
|---|---|
| `--preview` | 不写任何文件，只打印要对 `hooks.json` / `relaymesh.json` 做的**逐行改动**（`-` 删除、`+` 新增、前后各两行上下文）；确认无误后去掉它再执行一次 |
| `--dry-run` | 只打印计划，不打印逐行差异，同样不写文件 |
| `--no-status` | 只登记收件箱用的 `postToolUse` 与 `stop`，不登记状态上报事件；已经登记过的状态事件会被摘掉（别人的登记不动） |

真正写入之前，已经存在的 `hooks.json` / `relaymesh.json` 会被复制成同目录下的 `<原文件名>.bak-<时间>`，每个文件只留最近 3 份；备份失败就一个文件都不改。`uninstall` 摘掉我们的登记之前也会先备份。从旧版本升级（只有 `postToolUse` / `stop` 两个）时，重新执行安装命令即可补上其余八个。

装好之后 Cursor 通常会在保存 `hooks.json` 后重新加载；**已经打开的会话可能不会**，没生效时重启 Cursor 或新开一个会话。**工具栏的收件箱状态块会显示 `hook 刚刚`（点开写着「编辑器 hook 最近一次查询：刚刚」）**，这就说明 hook 已经在工作；如果一直显示 `hook 未装`（点开是「还没收到过查询」），往下看排错。

### `.cursor/relaymesh.json`

```json
{
  "workflow_id": "my-project-continuation",
  "mcp_url": "http://192.168.1.10:18775/mcp",
  "mcp_server": "relaymesh",
  "token_env": "RELAYMESH_TOKEN",
  "interval_seconds": 15,
  "enabled": true
}
```

| 字段 | 说明 |
|---|---|
| `workflow_id` | **必填**。这个项目里的智能体使用的工作流。换了工作流（比如迁移目录后新开了一个）要同步修改，或者重新执行 `install --workflow <新的>` |
| `mcp_url` | 可选。不填则取 `mcp.json` 里 `relaymesh` 条目的地址 |
| `mcp_server` | 可选。`mcp.json` 里那一项的名字，默认 `relaymesh`；只填了 `mcp_url` 时按地址匹配 |
| `token_env` | 可选。存放令牌的环境变量名，默认 `RELAYMESH_TOKEN`；没设置时回退到 `mcp.json` 的请求头或地址里的令牌 |
| `interval_seconds` | 可选。本机两次查询之间至少隔几秒，默认 15；`0` 表示不节流 |
| `enabled` | 设为 `false` 让这个项目的 hook 暂时安静（不用卸载） |

这个文件不含令牌，可以提交到仓库；但它绑定的是某一个工作流，**多台机器、多个工作流共用一个仓库时，建议把它加入 `.gitignore`**，各自 `install` 生成。同一个仓库的多个 git 工作树（worktree）共用一份被提交的配置时，每个工作树里的 hook 都会按它写的工作流汇报；由 Hub 发起的运行（「启用 Agent」、预设运行）会认领自己跑的那个对话，对话的状态与收件箱提醒仍归发起运行的工作流（见 `docs/terminal-operations.md` §8.11），但你在编辑器里亲手打开的对话没有这层保护，仍以这个文件为准。

### 令牌从哪里来

hook 运行时按下面的顺序找，**从不写入任何文件，也从不打印**：

1. 环境变量（默认 `RELAYMESH_TOKEN`，可用 `token_env` 改名）；
2. `~/.cursor/mcp.json` 里对应条目的 `Authorization` 请求头（支持 `${env:NAME}` 写法）；
3. 同一个条目的**地址里直接带着令牌**：`https://<服务地址>/mcp?token=…`、`/mcp/<令牌>`、`/mcp/token/<令牌>`，以及 ExecMesh 的能力网址 `/mcp/c/<令牌>`。控制台「复制 MCP 配置」给出的往往就是这种写法。请求会**原样发往这个地址**（能力网址只认地址里的令牌，放进请求头会被拒绝），令牌不会被搬到别处。

补充几条：

- 配置里写了 `mcp_url`、又点名了别的条目（`mcp_server`）时，只有两者指向**同一个服务**（协议、主机、端口都相同）才会采用条目地址里的令牌——令牌不会被发到别的主机；
- 配置里只写了不带令牌的 `mcp_url`、没有点名条目时，`mcp.json` 里「只差令牌」的那一项就是同一个服务；
- `relaymesh.json` 里手写的、带令牌的 `mcp_url` **不算**令牌来源（项目文件可能被提交），`status` 会提醒；`install --mcp-url` 遇到带令牌的地址会直接拒绝，什么都不写；
- 本机用来节流的临时文件只由工作流和脱敏后的地址决定，名字与内容里都没有令牌，轮换令牌也不会重置节流。

### hook 的节奏

**`postToolUse`**（每次工具调用之后）：

- 本机先节流：15 秒内已经问过就直接放过，不访问服务端，所以平时几乎没有开销；
- 问服务端时带上「我是 hook」的标记，由**服务端**按节奏决定要不要提醒：第 1 次立即，第 2 次至少 5 分钟后，第 3 次至少 15 分钟后，**每条追加最多提醒 3 次**；
- 需要提醒时，服务端给出一段现成的话，hook 原样作为 `additional_context` 交给智能体；没有未读或还没到时间就什么也不说。

**`stop`**（智能体准备结束这一轮）：

- 只在这一轮正常结束（不是被你中止、也不是出错）时才检查；
- 还有没读的追加，就用 `followup_message` 让智能体再多跑一轮去读它们；
- 每次收尾**只拦一次**（`loop_limit: 1`），拦过之后不会再拦，不会形成死循环；拦截**不消耗**那 3 次提醒的额度。

**出任何问题都不会妨碍你**：服务不可达、令牌过期、`mcp.json` 读不到、回复格式不对、超时（1.5 秒）……一律当作「没有可说的」，什么也不输出，hook 以成功状态退出。

hook 的查询不会被当成「智能体与 RelayMesh 在交互」：状态块里「Agent 最近一次与 RelayMesh 交互」只反映智能体自己调用工具的时间，hook 的查询单独显示为「编辑器 hook 最近一次查询」。

### 检查与排错

```bash
relaymesh-hook status
```

会检查并显示：用的哪个工作流、地址（已脱敏）、令牌来自哪里（不显示令牌）、hooks.json 里登记了什么、服务端是否连得通，以及当前未读几条。`status` 的查询**不会**计入网页上的「hook 最近一次查询」。

| 现象 | 多半是 |
|---|---|
| 状态块一直显示 `hook 未装`（点开是「还没收到过查询」） | 没装，或装的项目不是 Cursor 当前打开的那个；装好后 Agent 要调用一次工具才会触发 |
| `status` 说找不到令牌 | `mcp.json` 里没有 `relaymesh` 条目（用 `--mcp-server` 指定名字），该条目既没有 `Authorization` 请求头、地址里也没带令牌，或请求头引用的环境变量没设置；令牌只写在 `relaymesh.json` 的 `mcp_url` 里不算 |
| `status` 报 401 / 403 | 令牌过期，或这个令牌没有 `workflow_context` 的权限 |
| `status` 连不上 | `mcp.json` 里的地址在这台机器上不通；用自签名 HTTPS 时请改用 `http://` 的 MCP 地址 |
| 状态块显示 `提醒已关` | 设置里关掉了总开关或「编辑器 hook」，重新打开即可 |
| 提醒了但智能体没反应 | 提醒只是塞进上下文，是否照做取决于智能体；回执提示行与提示词条款会给它第二重提醒 |
| hook 报命令找不到 | `hooks.json` 里登记的是二进制的绝对路径；二进制被移动或删除后就找不到了。`relaymesh-hook status` / `doctor` 会提示登记的路径是否存在；重新执行安装命令即可（Windows 用页面上的 PowerShell 命令） |

### hook 汇报的运行情况（Agent 状态与会话守护用）

hook 除了查收件箱，还把「Agent 现在在干什么」报给服务端：网页上的 Agent 身份与状态（空闲 / 思考中 / 执行工具 / 等待批准 / 已中止 / 出错 / 已结束）和终端会话守护（`docs/terminal-operations.md` §8.5）都靠它。登记的事件一共十个：

| Cursor 事件 | 子命令 | 上报的事实 | 发送方式 |
|---|---|---|---|
| `postToolUse` | `post-tool-use` | 工具结束（工具名、耗时） | 同步：顺带问收件箱提醒 |
| `stop` | `stop` | 一轮对话结束（结束状态） | 同步：顺带问要不要拦一次 |
| `sessionStart` | `session-start` | 会话开始 | 分离子进程 |
| `sessionEnd` | `session-end` | 会话结束（原因） | 分离子进程 |
| `beforeSubmitPrompt` | `before-submit-prompt` | 用户提交了提示词（只报这个事实） | 分离子进程；永远放行 |
| `afterAgentThought` | `after-agent-thought` | 正在思考 | 分离子进程；同一对话 5 秒内最多一次 |
| `preToolUse` | `pre-tool-use` | 工具开始运行（工具名） | 分离子进程 |
| `afterAgentResponse` | `after-agent-response` | 回复了一段话（只报这个事实） | 分离子进程 |
| `postToolUseFailure` | `post-tool-use-failure` | 工具失败（工具名、耗时） | 分离子进程 |
| `preCompact` | `pre-compact` | 正在压缩上下文 | 分离子进程 |

**只报「发生了什么」，从不报内容。** 每次上报只由下面这些字段构成：事件种类、发生时间（用来修正本机与服务端的时钟差）、Cursor 对话编号、工具名（只留字母数字与 `_:.-`，最长 64 个字符）、工具耗时（毫秒）、结束状态 / 原因（小写字母与下划线，最长 16 个字符）、客户端类型（`cli` / `ide`，能判断才报，拿不准就不报）、Cursor 版本号、项目目录。提示词、思考、回复、工具的参数与输出、对话记录的位置、邮箱（载荷里的和环境变量里的）一概不读、不转发；分离出去的子进程收到任务后还会按同一份白名单再清洗一遍。有静态测试守着：源码里不许出现读取邮箱的代码。

**不拖慢 Cursor。** 要等回复的两个事件（`post-tool-use`、`stop`）仍是同步的，`post-tool-use` 在本机节流放行时把状态字段并进同一次查询，被节流时才另起子进程补报，所以不会多一次请求。其余八个事件，hook 进程只生成上报、交给一个**分离出去的子进程**（`relaymesh-hook report`，自成会话 / Windows 下脱离控制台）就立刻返回——即使服务端 1.2 秒才回，hook 进程也只花几毫秒；子进程自己解析令牌（令牌不经过命令行与标准输入）、最多等 1.5 秒、发完即退。服务端连不上时，子进程会留下一个 30 秒的**熔断标记**，期间不再起新的子进程，免得服务端挂了时满地都是等超时的进程。

**出任何问题都静默放行**：起不了子进程、写不了临时文件、服务端不可达……一律当作「没有可说的」，不影响你和智能体。

**新 hook 连旧版服务端也不会出错**：旧服务端会忽略它不认识的字段与事件；`postToolUse` / `stop` 沿用旧的上报名（`tool` / `stop`），守护照旧工作，只是没有上面那八个事件带来的 Agent 状态。

- `stop` 事件里，被中止或出错的收尾**仍然不会被拦**，但会把结束状态报给服务端；
- 已经装过 hook 的项目，重新执行安装命令即可更新（幂等，改动前先备份）；没更新时一切照旧，只是服务端拿到的状态依据少一些。

### 从旧的 Python hook 迁移

早期的 hook 是一份 Python 脚本（`relaymesh-inbox.py`），现已移除：服务端不再提供它，也不再维护。还装着它的项目按下面几步换成 Go 版：

1. 在项目根目录执行会话页复制的 **Go 安装命令**（`install.sh` 一键装），或已下载二进制时：`relaymesh-hook install --workflow '<你的工作流>'`。
2. `install` 会**只替换** `hooks.json` 里含 `relaymesh-inbox.py` / `relaymesh-hook` 的条目，保留其他 hook（如 `halt-guard.sh`）；`relaymesh.json` 工作流与地址键保留，仍不含令牌。
3. 确认：`relaymesh-hook status`（连通性正常）；收件箱芯片显示「hook 刚刚」；顶栏执行图标随 hook 事件变化。
4. 项目里 `.cursor/hooks/relaymesh-inbox.py` 这个文件不会被自动删除（`install` 只处理 `hooks.json` 里的登记），确认迁移成功后可以手动删掉。

### 用户级安装与卸载

```bash
relaymesh-hook install --user --scope user   # 装到 ~/.cursor，对所有项目生效（每个项目仍要有自己的 .cursor/relaymesh.json）
relaymesh-hook uninstall
relaymesh-hook uninstall --purge             # 连 relaymesh.json 一起删
```

卸载只动脚本自己登记的条目，其他 hook 不受影响。

## 安全与隐私

- hook 脚本里没有任何凭据；令牌只在运行时从环境变量或你本机的 `~/.cursor/mcp.json`（请求头，或写在地址里的令牌）读取，不写入项目文件、不打印（`status` 与日志里的地址都已脱敏）、不上传到别处；脚本只和你配置的 RelayMesh 地址通信；
- hook 只调用 `inbox_peek`：只读，不会读取追加的全文，也不会改变它们的状态——全文只有智能体自己调用 `inbox` 时才交出；
- 回执提示行与 hook 提醒里只带最新一条的**开头**（约 160 字）；
- 收件箱里的内容与你平时的反馈一样，只在你的 RelayMesh 服务里保存，未被取走的 7 天后自动过期。

## 没有做的事

**不打断正在进行的会话。** 让编辑器立刻停下当前这一步，需要操作编辑器里那个会话本身，超出了 MCP 服务端的职权范围。hook 只在两个自然的间隙出声：每次工具调用之后、准备收尾之前。要立刻让智能体停下，仍然是在 Cursor 里手动操作。
