# 项目、知识库与授权

项目把一个团队或产品相关的工作流、文档、任务和授权收在一起。这一篇讲项目是什么、知识库与模块怎么组织、访问控制的三个档位、谁能读写什么，以及被拒绝时该怎么办。

## 项目是什么

- 项目是知识库与产物的归属单位，一个项目对应多个（主机，目录）：智能体在哪台主机的哪个目录里工作，决定了它属于哪个项目。一个目录只属于一个项目。
- 项目只能由用户在 Web 的 `/projects` 页面创建与确认，智能体没有创建入口。
- 工作流属于哪个项目，由它绑定的（主机，目录）决定。还没归入项目的工作流，仍然能用文档库（`/docs/<工作流>`），在项目页把它归入后才进入项目知识库。
- 项目可以归档；项目换了目录、搬到另一台机器之后，旧工作流的改绑见 `project-migration` 主题。

## 知识库、模块与文档

- **知识库**是项目里跨工作流的文档库：文档列表、搜索、模块、推荐结构都在项目页的「知识库」页签里。每个工作流自己的会话工作表放在 `sessions/<工作流>/` 下。
- **模块**是项目的功能模块，路径是**封闭列表**：文档、任务都只能标注已有的模块路径，不会各写各的。模块有标题、说明和负责人（一个智能体身份）。模块在项目页的「模块」页签里维护。
- 设计信息绑定到模块路径；对一个模块路径授权时，它下面的子路径也在授权范围内（`chat` 的授权覆盖 `chat/flow` 这样的子路径）。
- 文档的读写、修订、决策卡与导入导出见 `project-docs` 主题；任务清单见 `shared-task-board` 主题。

## 访问控制的三个档位

每个项目有一个访问控制档位（`acl_mode`），新建项目默认是 `audit`。档位只由用户在项目页「管理」页签的「设置」小节里改（那里也能改项目名称与说明、管理归入项目的目录）。「管理」页签一共有四个小节：设置、迁移、授权、审计。

| 档位 | 行为 |
|---|---|
| `off` | 不判定、不记录，所有调用照常通过 |
| `audit` | 不拦截任何调用；只把「若强制执行会被拒绝」的调用记进审计，用来观察一段时间 |
| `enforce` | 规则真正生效，不够权限的调用被拒绝 |

切到 `enforce` 之前，先到项目页的审计里确认「若强制执行会被拒绝」的记录已经很少。强制执行后，没有在调用里声明身份（`project_directory` 与 `host_name`）的智能体，写入会被拒绝。

## 调用方怎么被认出来

- 智能体的身份来自它在调用里带的 `project_directory` 与 `host_name`，以及工作流和它们的绑定。治理类工具的调用都应当带上这两个参数。
- **这不是安全边界**：身份是调用方自报的。这套规则防的是误操作、越权写入和「拿着别人的编号就去改」，真正的边界仍然是令牌（见 `credentials-and-permissions` 主题）。
- 没带这两个参数时，Hub 只能按工作流绑定的目录去推断调用方，审计里记作 `assumed`；在强制执行档下，没有声明身份的写入会被拒绝。

## 谁能做什么

权限等级逐级包含：`read` ⊂ `comment` ⊂ `edit` ⊂ `manage`。判定按下面的规则取**最高**的一条：

| 规则 | 谁得到什么 |
|---|---|
| 用户（Web 登录者） | 任何地方都是 `manage`，不受档位限制 |
| 负责范围 | 文档的负责人、文档所在模块的负责人、工作流绑定的身份，对自己负责的资源是 `manage` |
| 同一项目 | 同一项目里的智能体，对项目的知识库、模块和项目目录是只读（`read`），对别的工作流的会话数据不适用这一条 |
| 知道工作流编号 | 只读那个工作流的会话数据（任务、历史、会话文档）；不含它的收件箱，也不含项目知识库的其余部分 |
| 显式授权 | 按授权的范围与角色，见下一节 |
| 收件箱 | 只有它的所有者能读写（读取会把消息标成已送达，等于写），不走授权 |
| 都不满足 | 拒绝，回执里写明缺什么、怎么补 |

读需要 `read`，写需要 `edit`，授权和改负责人需要 `manage`。

## 授权（grant）

- **范围**有五种：`project`（整个项目）、`module`（一个模块及其子路径）、`doc`（一篇文档，写路径或文档编号）、`workflow`（一个工作流的会话数据）、`tasks`（项目任务板的管理权，只覆盖任务，不等于能编辑文档）。
- **角色**最高到 `edit`：`manage` 不能转授，只能由用户或负责范围自动得到。
- **谁能授权**：用户在项目页「管理」页签的「授权」小节里授权；对某个资源有 `manage` 的智能体（例如模块负责人）可以用 `project_docs` 工具的 `grant` 动作把 `edit` 以下的权限授给别的身份，参数有 `grantee`（被授权的身份）、`grant_scope`、`grant_ref`、`role`，可选 `expires_hours`（有效小时数）。`grants` 动作列出现有授权，`revoke` 动作撤销。**例外**：`tasks` 范围（项目管理 Agent）只有用户能授予，角色只能是 `edit`，对象只能是单个智能体身份，智能体不能自授也不能转授。
- 授权可以撤销，也可以带有效期；撤销或过期的授权不再起作用。授权的对象可以是一个身份，也可以是群（「群共享」就是对群的一条只读授权）。
- 完整动作与参数以 `project_docs` 工具自己的说明为准。

## 项目管理 Agent（任务管理）

- 项目管理 Agent 是用户在项目页「管理」页签的授权小节里、「任务管理」下面勾选出来的智能体：目录归在本项目里的智能体逐个列出，勾选就是授予 `tasks` 范围的编辑授权，取消勾选就是撤销。**默认没有任何管理 Agent，只有用户能勾选**，被勾选的智能体的收件箱会收到通知。
- 它能把任务派给同一张任务板上的其他工作流、编辑所有人的任务、验收承接者的交付；没有被勾选的智能体，只能管理自己创建或承接的任务。分工细节见 `shared-task-board` 主题。
- 持有整个项目范围、角色在 `edit` 以上的授权，也等于管理 Agent（项目级编辑本来就包含改所有任务）。
- 任务管理权只认显式授权，没有「同项目只读」「负责人」「知道编号」这些隐含规则；它的判定一律按强制执行档算，项目在 `off` 或 `audit` 档时也不会因为档位放宽管理权。
- 如果这个智能体的令牌另外带有 `launcher` 权限位，管理 Agent 还能用 `preset_run` 运行本项目里已有的「非交互续聊」预设，去唤醒任务板上的子会话，见 `credentials-and-permissions` 与 `terminal-operations` 主题。

## 被拒绝了怎么办

1. 先读回执里的原因：它会写明缺什么角色、你在这里只有什么角色。
2. 如果是「没有可识别的身份」，在调用里补上 `project_directory` 与 `host_name`。
3. 如果是角色不够：写入只来自自己的负责范围、用户的授权，或负责人智能体的授权。请用户在项目页授权，或请负责人智能体用 `grant` 授权；用 `async_ask` 把这件事发给用户（见 `confirm-items` 主题）。
4. 不要绕开规则：不要借别人的 `project_directory` 或编号去改别人的东西。
5. 项目在 `audit` 档时，超出规则的写入并没有被拦下，只是被记下；这类记录在审计里标着「已放行 · 强制执行会拒绝」。

## 审计

项目页「管理」页签的「审计」小节回答「谁在什么时候对项目做了什么」。审计从不记录文档正文和聊天正文。

- 每条记录有一个结果：`allow`（放行）、`deny`（被拒绝；在 `audit` 档表示「若强制执行会被拒绝」，并没有真的拦下）、`assumed`（调用方没有声明身份，按工作流绑定推断）。
- 常见动作：`acl.denied`（一次被拒绝的访问）、`doc.write`、`doc.delete`、`doc.read.cross`（跨工作流读文档）、`write.cross`（跨工作流写任务、会话数据等）、`grant`、`revoke`、`module.write`、`project.create`、`project.update`、`project.dir_add`、`project.dir_remove`、`project.migrate`、`launcher.run`（项目管理 Agent 运行了预设），以及群与身份相关的 `group.*`、`identity.rename`、`identity.disable`、`wake.manual`。
- REST 查询：`GET /api/v1/audit?project=<项目>&action=<动作>`（需要 Web 登录），每条记录的 `detail` 是一段 JSON 字符串。
