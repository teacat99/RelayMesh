# 远程终端与模型执行：升级、回滚与数据位置

这份文档回答四个运维问题：升级或回滚时会发生什么；终端内容与模型运行输出分别存在哪里、谁能看到；从 v1.6.x 升级到 v2.0.0 有哪些行为变化；经 SSH 网关接入的主机怎么运作、能信任到什么程度（第 4 节）。功能本身的说明见 [README](../README.md)，从独立 ExecMesh 迁移的对照见 [execmesh-migration.md](execmesh-migration.md)。

## 1. 升级与回滚

### 1.1 服务端（Hub）

- **数据库迁移只增不改**：新版只会新增表和列，不改、不删已有数据。因此旧版二进制可以直接打开新版升级过的数据库：升级 → 回滚 → 再次升级的往返演练中，令牌、会话、工作流笔记全程完整，新旧两个阶段写入的数据都读得到（可重复运行：`bash scripts/e2e-holder/skew.sh`，仓库开发者使用）。发布前还用公开的 v1.6.3 做过同样的往返演练：令牌、会话与回复、草稿、笔记、规范和设置全程完整，唯一的差别是会话阶段按 §3 第 9 条收敛。
- **回滚不会放大权限**：新版创建的 ExecMesh 档令牌（只有终端权限）在旧版里没有任何可用工具，因为旧版不认识终端权限位；再次升级后它恢复原样。旧令牌的终端权限位在迁移后缺省为关闭，升级本身不会让任何已有令牌多出终端能力。
- **升级前请备份**：停止服务后复制 `data/relaymesh.db`（以及同目录的 `-wal`、`-shm` 文件）；不想停服务，可以用 `sqlite3 data/relaymesh.db ".backup 'backup.db'"`。Docker 部署请记下当前镜像标签，回滚就是换回旧标签再 `docker compose up -d`。
- **模型执行等能力在升级后仍是关闭的**：`RELAYMESH_TERMINAL_EXEC`、`RELAYMESH_TERMINAL_FILES` 默认不设，升级本身不会开启任何模型执行或文件能力；开启它们需要你显式设置环境变量、给令牌授权终端权限与主机、并在主机页打开「允许模型访问」（见 README）。

### 1.2 Agent 与会话守护进程

- **升级 Agent 不会打断会话**：`relaymesh-agent install` 默认装成两个服务单元，Agent 与「会话守护进程」分开运行。升级只替换并重启 Agent；守护进程里的终端会话和正在运行的模型命令不受影响，新 Agent 接上后还是同一个会话、同一个 Shell。
- **其他主机上的 Agent 怎么升级**：Agent 默认不会自动升级（下面的「自动升级」默认关闭：提示模式只提醒，静默模式由主机所有者在本机明确开启，并且只安装验过发布签名的新版本），服务端也不会把程序推送到主机上——升级始终是**主机自己去取**，我们刻意不做「服务端往主机下发可执行代码」的通道（那会把服务端的失陷变成所有主机上的任意代码执行）。服务端提供的是**提醒**（主机清单给版本落后的 Agent 标「可升级」）、**受控的取件**（只为这一台主机开的升级窗口）和**需要主机所有者先点头的一键升级**。「最新版本」取自服务端安装目录里的 `VERSION`，缺失就不提醒；版本比较时 dev 构建比它的基线发行版新，同日不同提交无法排序、无法解析的版本一律按「不同」处理，版本为空或更新的主机不提醒。**但版本号不等于「Agent 代码变了」**——服务端每热更一次，版本号就跟着整个仓库的构建变一次，哪怕 Agent 依赖的代码一行没动；所以两边都带着「Agent 侧代码指纹」时，提醒只看指纹（见下条「Agent 侧代码指纹」）。两条路径：
  - **一键升级（默认关闭，由主机所有者在本机允许）**：在主机上执行 `relaymesh-agent web-upgrade on`（`off` 关闭、`status` 查看；开关只存在主机本地，服务端无法替你打开），Agent 几秒内就会告知服务端。之后管理员在 Web 的「升级 Agent」对话框点「升级到 X」：Agent 自己从服务端下载新版本（文件名由 Agent 按自己的系统与架构推出，不接受服务端指定的地址），校验 SHA-256，试运行 `version` 确认报出的就是预期版本，再交给 `systemd-run` 起的独立升级进程替换程序并**只重启 Agent**；新版本没有在约 90 秒内连上服务端，就自动还原旧版本，并把原因带回 Web 显示。要求：Linux、由 systemd 管理的常驻服务（系统级或用户级）；macOS、Windows 与前台运行的 Agent 暂不支持，界面会说明并继续给下面的命令。同一台主机同一时间只允许一次升级，已经是服务端自带的版本（或更新）不会再升级。开启一键升级，等于信任这台服务端发布的 Agent 程序：不想这样，就保持关闭，用升级窗口。
  - **自动升级（提示模式与静默模式；默认关闭，由主机所有者在本机开启，服务端另有一道总闸，也默认关闭）**：在主机上执行 `relaymesh-agent auto-upgrade enable --mode notify`（`disable` 关闭、`status` 查看；同意文件是 `<数据目录>/auto-upgrade.json`；开关只存在主机本地，服务端无法替你打开，修改后几秒内 Agent 重新握手生效，不需要重启服务）。开启后，Agent 在被批准、连上服务端之后随机等 10~40 秒检查一次（避免整批主机同时问），之后约每 6 小时一次；没得到确定答案（总闸关着、服务端暂时没有适用的程序、没有回答）时约每 15 分钟再问一次，所以管理员事后打开总闸也很快生效。检查只问服务端「我是不是比你自带的更旧」：服务端的回答只带状态与版本号，不带下载地址、校验值或文件名；Agent 还会自己再比较一遍，只有本机能证明版本更旧才算有新版本——版本相同、更新，或无法比较新旧（本地构建、同日构建）一律当作已是最新，**版本只升不降**。**提示模式只做提醒：不下载、不升级**——结果只记在日志与 `relaymesh-agent auto-upgrade status` 的输出里，并显示在 Web 主机卡片上的「自动升级：提示 · 有新版本」标签（悬停有最近一次检查的时间与结果）；要升级仍按上面的一键升级或升级窗口。要求：Linux、由 systemd 管理的常驻服务（系统级或用户级）；其他系统与前台运行的 Agent 开启时会被明确拒绝并说明原因。**服务端总闸**在「设置 → 终端偏好 → Agent 自动升级」（默认关闭）：关着时服务端对所有主机的检查一律回答「总闸关着」，打开或关闭都需要重新输入密码（解锁）并写审计 `agent_auto_upgrade_switch`（只记 `enabled=true|false`）；它不改动任何主机，只决定服务端肯不肯回答。旧服务端不认识这个检查（Agent 记一次「没有回答」，稍后再问），旧 Agent 不声明这项能力（卡片上没有任何标签）。**静默模式**（Agent 自己下载、验证后升级）见下一条。
  - **静默模式（`--mode silent`；由 Agent 自己发起升级，仍然只有主机所有者能开）**：`relaymesh-agent auto-upgrade enable --mode silent [--window HH:MM-HH:MM] [--trust-key rmpub1:<公钥>]`（官方发布的 Agent 已经编进了发布公钥，通常不需要 `--trust-key`）。它与提示模式的区别是：Agent 检查到有新版本后，会**自己**向服务端提出升级请求（只带请求编号与版本号），不需要有人点按钮。服务端按顺序核对：总闸已打开；这台主机的所有者在本机选了静默模式（连接握手里声明）且不是临时身份；版本确实更新、而且正是服务端当前的最新版本；服务端安装目录里有这个版本的发布签名文件（`relaymesh-agent-<平台>.sig`，只给 Agent 下发，不对外提供下载）；主机上没有会被打断的活动会话（独立守护进程托管会话的主机不受影响）；没有别的升级请求在进行。全部满足才为这一台主机开升级窗口，并下发一次性票据、校验值与签名；任何一条不满足就只回答原因（总闸关着、主机没同意、已是最新、版本已过期、暂时没有适用的程序、未签名、主机忙、请求太频繁），不开窗口、不动主机。Agent 拿到批准后：下载 → 核对 SHA-256 → **用可信公钥验证 ed25519 发布签名（验签通过之前绝不运行下载来的程序，连 `version` 子命令也不会）** → 比较版本 → 再核对一次本机的同意（所有者中途关闭就放弃）→ 交给独立的升级进程（新版本连不上服务端会自动还原；独立守护进程不会被重启，会话原样保留）。**可信公钥**是「编进程序的发布公钥」与「所有者用 `--trust-key` 写进 `auto-upgrade.json` 的公钥（最多 8 把）」的并集；并集为空时 `enable --mode silent` 会被拒绝。`relaymesh-agent auto-upgrade keys` 列出这个程序编进了哪几把（标识 + `rmpub1:…` 公钥，不需要任何权限，也不读本机配置），`status` 里会写「编进程序 N 把（标识 …） · 本机钉住 M 把」，方便你与发布方公布的标识核对。自己构建 Agent 时默认连同官方发布公钥一起编进去；想换成自己的名单，构建时加 `-ldflags "-X github.com/teacat99/RelayMesh/v2/internal/relsign/trust.override=rmpub1:<公钥>[,rmpub1:<公钥>…]"`（`=none` 表示空名单，此时只认 `--trust-key`）。所以服务端即使被攻破，也无法让主机装上没有发布私钥签名的程序。**每个具体版本最多自动尝试 2 次**（尝试在下载之前就记在本机；重新 `enable` 或 `disable` 会清零；记录读不了就暂停自动升级），避免坏版本被反复重试。`--window` 是主机本地时间的时间段（24 小时制，可以跨午夜，起止不能相同），**只约束静默模式什么时候开始升级**：时间段之外 Agent 照常检查、记下「有新版本」，但不发请求；时间段对 Web 一键升级与升级窗口没有影响。审计事件：`agent_auto_upgrade_start`（批准下发之后记）、`agent_auto_upgrade_ok`、`agent_auto_upgrade_fail`（带失败码，例如 `signature`）、`agent_auto_upgrade_rollback`。Web 主机卡片上的标签会如实写出状态（「自动升级：静默」「· 总闸关」「· 有新版本」「· 未签名」「· 刚升级完成」「· 上次升级失败」），悬停有说明。**哪些版本带签名**：维护者在发布机上用离线保管的发布私钥，给要发布的 Agent 程序逐个签名（签名与程序的字节一一对应，签名文件放在服务端安装目录里，只发给 Agent）；签名之前还会用那个镜像里真正要发布的 Agent 程序核对「这把钥匙确实在它的可信名单里」，避免签出一份所有主机都不认的签名。公共流水线（GitHub Release、Docker Hub 上的公共镜像）构建出来的程序**没有**这把私钥，构建时不会产生签名——直接用公共镜像的服务端回答静默主机的永远是「未签名」，不批准、不升级；提示模式、Web 一键升级与升级窗口都不依赖签名，对所有版本照常可用。想让自己部署的服务端也支持静默升级，需要自己持有一对密钥、给自己的发行物签名，并让主机用 `--trust-key` 信任自己的公钥。**另一条路（2.0.0 起）：用维护者补签的 Release 资产。** 每次正式发布之后，维护者会在发布机上给 GitHub Release 里的 5 个 Agent 程序补签，并把对应的 `relaymesh-agent-<平台>.sig` 作为资产挂到同一个 Release 上（资产列表里有 `.sig` 才算补签完成；刚发布的一小段时间里只有程序和 `checksums.txt`）。把 Release 里的 Agent 程序连同对应的 `.sig` 放进你服务端的 Agent 分发目录（`RELAYMESH_AGENT_DIST_DIR`；Docker 镜像里是 `/app/agent-dist`），并把该目录里的 `VERSION` 文件写成与 Release 标签**完全一致**的字符串（例如 `v2.0.0`），这台服务端就能批准静默升级——官方发布的 Agent 已经编进了对应的公钥，主机不需要 `--trust-key`。**限制**：签名与文件的字节一一对应，只对 Release 里那几个文件有效，Docker Hub 的公共镜像是另一次构建、字节不同，不能与 Release 的签名互换；服务端读的是自己分发目录里的 `.sig`，不会去 GitHub 取，所以单是 Release 上挂着 `.sig`，并不会让任何服务端自动支持静默升级。**更换发布密钥必须分两步**：一份签名要能被「已经装在主机上的那一版 Agent」验过，所以先发一版把新公钥加进名单、仍用旧钥签名，等主机升上去之后，再切换签名用的钥匙；一步到位会让所有已经装好的主机拒绝新版本。名单里除了主钥还有一把备用钥（私钥离线另存），主钥丢失时备用钥能继续签名，不会让所有主机卡在旧版本。
  - **安装时一并开启自动升级（`install --auto-upgrade`，默认不带）**：`relaymesh-agent install … --auto-upgrade notify|silent [--auto-window HH:MM-HH:MM]`（`--auto-window` 只用于 `silent`，写法与 `auto-upgrade enable --window` 相同）。同意仍然只写在这台主机本地：服务装好之后才写 `auto-upgrade.json`，与手动执行 `auto-upgrade enable` 完全等价。只有 Linux + systemd 常驻服务支持；其他系统、写法有误（例如把 `--auto-window` 用在 `notify` 上、时间段不合法），或这个程序没有编进发布公钥却选了 `silent`（自己编译的版本可能如此），都会在**动系统之前**就被拒绝，不会装一半。服务已经装好、但写同意文件失败时（例如数据目录不可写），服务保持已装好的状态不回滚，命令以退出码 1 结束并打印补开的那条 `auto-upgrade enable …` 命令；重复执行安装命令不会换掉机器码。Web 的「接入主机」里生成安装命令时，Linux + 常驻服务下多一个「自动升级」选项（「不开启 / 提示新版本 / 静默升级」，默认「不开启」；静默可再填时间段，写错时命令不会生成；只有使用服务端自带的安装源才能选，否则置灰并说明原因），选了才会在命令末尾加上这两个参数，选项旁的说明会写明它做什么、怎么收回；升级命令（`upgrade`）不带这两个参数。
  - **主机上还有活动会话时**：点击之前界面就会提醒——有几个运行中的会话、其中几个此刻有人在看、几个在跑全屏程序，以及进行中的模型运行。会话由独立的守护进程持有时，升级不会中断它们（已经打开的终端页面会短暂断开，Agent 回来后自动重连）；没有守护进程（会话与 Agent 同生共死）时，升级重启 Agent 会结束这些会话，界面改用更醒目的提示。两种情况都要**二次确认**才会真正发出请求；服务端同样会核对，没有确认就拒绝（HTTP 409，并带回它刚核对到的会话摘要），所以界面看漏了新开的会话也不会误升。
  - **升级窗口 + 命令（任何主机都可用）**：点开「升级 Agent」，按主机的操作系统生成升级命令，并同时为**这一台**主机开一个升级窗口——默认 10 分钟，可「延时」（每次 +10 分钟，剩余时间最长 60 分钟）或「提前结束」；票据 128 位随机、只在服务端内存里（服务端重启即全部关闭）；窗口只放行 `/i/` 里本来就公开的安装脚本、校验文件与各平台 Agent 二进制，所有失败一律同一个 404。命令要在主机上执行，本质是 `relaymesh-agent upgrade`（用户级安装加 `--user`）：原子替换 Agent 程序并只重启 Agent 服务，不改服务单元，也不替换、不重启会话守护进程（里面的会话不受影响）。主机以不同版本重新上线、被停用 / 删除或窗口到期，窗口自动关闭；开启、延时、结束与到期都写审计（`upgrade_window`，不记录票据）。
  - **审计**：每次一键升级的发起、交接、完成与失败都写审计事件 `agent_web_upgrade`（含发起人与目标版本，不含任何票据）；Agent 自动升级总闸的开关写 `agent_auto_upgrade_switch`；静默升级的批准、完成、失败与自动还原写 `agent_auto_upgrade_start` / `_ok` / `_fail` / `_rollback`（含目标版本与失败码，不含票据与签名）。
- **想让守护进程也换成新版**：执行 `relaymesh-agent holder restart`。这会结束其中的会话，**也会终止模型正在运行的命令**（命令会先让你确认，并写明有几个会话、几条模型命令）；加 `--drain` 则不再接受新会话和新命令，等运行中的会话与模型命令都自然结束后再退出，不会打断它们（模型命令最长可以跑 7 天，所以排空可能等很久；`relaymesh-agent holder status` 能看到还剩什么）。**注意旧守护进程**：本次修复之前启动的守护进程统计不到模型命令，它的排空也只等会话、不等模型命令——换上新版的第一次重启面对的恰好就是这种旧守护进程，命令行会明说这一点；确认主机上没有运行中的模型命令再重启即可。安装参数改变后（例如 `--no-record`、`--deny-model-exec`）守护进程也要重启才会采用，安装器只会提示，不会替你重启。
- **`holder restart` 照抄不一定能用——升级 / 安装结束时打印的那一行已经替你拼好了**：升级命令的收尾会按这台主机的实际情况打印整条重启命令（见下），直接复制那一行即可。会让裸命令失败的有三种情形：
  - **命令找不到**（`command not found` / PowerShell 的「无法将 relaymesh-agent 项识别为 cmdlet」）：用户级安装把程序放在 `~/.local/bin`，登录 shell 不一定把它加进 PATH；Windows 装在 `C:\Program Files\RelayMesh Agent\`，从来不在 PATH 里。此时提示里会写完整路径，Windows 写成 PowerShell 的调用运算符形式：`& 'C:\Program Files\RelayMesh Agent\relaymesh-agent.exe' holder restart`。
  - **报「会话守护进程没有运行」，但它其实在跑**：系统级安装（`sudo` 装的）的守护进程以 root 运行，套接字在 `/var/lib/relaymesh-agent/holder/holder.sock`；普通用户直接执行时，命令按当前用户的默认位置（`~/.local/state/relaymesh-agent/holder/holder.sock`）去找，当然找不到。提示里会带 `sudo`；而你自己执行 `holder status|restart|stop` 失败时，如果这台机器上装了系统级的守护进程服务，命令会指出原因并给出 `sudo …` 写法（你明确用 `--holder-socket` / `--data-dir` 指了别的位置时不替你猜）。Windows 的系统级安装同理，要在「以管理员身份运行」的 PowerShell 里执行。
  - **套接字不在默认位置**（安装时用了自定义 `--data-dir`）：提示里会带上 `--holder-socket <路径>`。
  - **Windows 不需要等**：守护进程由计划任务拉起，兜底的看门狗触发器每 5 分钟才触发一次；`holder restart` 在守护进程退出后会直接启动它的计划任务，不用干等。Windows 的守护进程同样不会随 `upgrade` 一起换版本——想让它也换上新版，仍要执行一次 `holder restart`（没有重要会话时再做，这只是提醒）。
- **Agent 侧代码指纹（判断「要不要升级」「守护进程是不是旧代码」的依据）**：版本号（如 `v1.6.3-dev-20261016-c26a452`）跟着**整个仓库**的构建走，服务端每热更一次就变；以前拿它与主机一比，所有主机立刻都亮「可升级」，升级之后又提示「守护进程是旧版本」，其实 Agent 代码根本没变。现在构建时会给 Agent 算一个**代码指纹**：对 Agent 二进制依赖的那 13 个包（`cmd/relaymesh-agent`、`internal/agent/…`、`internal/termproto`、`internal/termstate`、`internal/secure`、`internal/sshexec` 等，外加 `go.mod` / `go.sum`）里所有非测试 `.go` 文件的内容取 SHA-256 前 12 位（换行统一成 LF，与构建机、Git 提交、Go 版本无关；`go run ./cmd/agentrev` 可以随时算出来，另有测试保证依赖目录与 `go list -deps` 一致，新增依赖却忘了登记会让测试失败）。它编进 Agent 与守护进程，握手时自报（`agent_rev`、`holder.rev`），服务端自带的这批 Agent 的指纹写在安装目录的 `REV` 文件里（与 `VERSION` 同时生成，同样不会被 `/i/` 发出）。规则：
  - **两边都有指纹**：只比指纹。一致 = Agent 代码完全一致，不提醒（主机清单展开后写明「与服务端自带的 X 代码一致」，一键升级也会以「代码完全一致，不需要升级」拒绝）；不同才提醒——版本号能确定更旧标「可升级」，版本号无法比较新旧（例如同一天的两次构建）标「代码有更新」；主机的版本号反而更新（服务端回退过）则不拿较旧的一批去降级主机。
  - **任何一边没有指纹**（旧版本 Agent、没有 `REV` 文件的旧镜像、本地 `go build` 的非发布构建）：回退到只比版本号，与引入指纹之前完全一致。已经装着的旧 Agent 升级一次就会开始自报指纹，在那之前仍按版本号提醒。
  - 指纹**随主机落库**，所以离线主机的「可升级」判断也照常；展开主机详情还会显示守护进程自己的版本号，并注明「（代码一致）」或「（代码较旧）」（守护进程版本与 Agent 相同时不显示）。`relaymesh-agent holder status` 也会打印守护进程的代码指纹；升级 / 安装结束时若守护进程与新程序的指纹一致，会直接说明「不需要重启守护进程」，不再让你白白担心要不要结束会话。
- **「守护进程较旧」徽标**：终端会话是守护进程创建的，所以守护进程里的改动（例如与「新建会话」有关的修复，会话字符集见 §5）要等它重启后才生效，光升级 Agent 不够。判断依据按精确程度依次是：（1）主机 Agent 与守护进程都带着代码指纹（见上条）时只比指纹——一致说明守护进程跑的就是现在这份代码，不显示徽标；不同才标「守护进程较旧」，这一条不看版本号，对 Windows 主机同样适用；（2）任何一边没有指纹（旧版本）时回退到能力位：守护进程每次启动都会声明自己具备哪些能力，在线的 Linux / macOS 主机上的守护进程没有声明某项修复所需的能力时，标「守护进程较旧」，Windows 主机不涉及 locale，这条旧路径不对它显示。悬停可看原因与做法。它只是提醒，不会替你重启；等没有重要会话时再执行 `holder restart`（或 `holder restart --drain`）即可，重启后徽标自动消失。
- **本地协议版本**：Agent 与守护进程之间、Agent 与服务端之间各有一个协议版本号，不一致时双方都明确拒绝并写明原因（日志里可见），Agent 会放慢重试，而不是反复冲击。目前三者都是 1，新旧版本可以混用。
- **内嵌模式**（`--holder embedded`，或 Windows 上没有安装守护进程时自动回落）：会话与模型命令随 Agent 进程结束；与服务端的断线重连不会影响它们。适合临时排障，常驻使用请用默认的两单元安装。
- **回滚 Agent**：回到不含守护进程的旧版本之前，先执行 `relaymesh-agent uninstall`（有运行中的会话时会先确认；先卸载 Agent、再卸载守护进程），再安装旧版。否则守护进程会继续持有旧会话，而旧版 Agent 并不知道它的存在。

### 1.3 服务端与 Agent 的版本混用

升级顺序不一致、或服务端回滚而 Agent 已经升级，都是常见情况，下面两种混用都已实机演练：

| 组合 | 行为 |
|---|---|
| 旧服务端 + 新 Agent | 连接、发现与启用、开会话、输入输出、会话列表全部正常；新 Agent 多出的能力（模型执行、文件）旧服务端不使用 |
| 新服务端 + 旧 Agent（v1.6.3 开发版及更早） | 人工终端完全正常；对这台主机的模型执行**立即**返回 `host_unsupported`（不挂起），`terminal_targets` 里标记 `usable=false`、`blocked=host_unsupported`；升级 Agent 后恢复 |

### 1.4 删除主机与设备端的清理

在 Web 上删除主机只让服务端忘记它（并终止其上的会话），**设备上的 Agent 与数据不会自己消失**：Agent 会按间隔继续尝试连接，被服务端拒绝。要连设备端一起清理，有两种办法：

- **删除时勾选「同时卸载设备端」**：仅当这台 Agent 在线、版本支持、并且装成了常驻服务（Linux systemd / Windows 计划任务）时才会出现。Hub 在删除前向 Agent 下发卸载请求，Agent 在本机另起一个与自身进程树无关的卸载进程，执行等价于 `relaymesh-agent uninstall --purge` 的流程；之后 Agent 在 3 分钟内不会再重连。请求被受理即返回，卸载在设备上异步完成。该操作与删除主机一样需要登录与再次验证密码，并写入审计（`uninstall=requested|offline|unsupported|failed`）。
- **在设备上手动卸载**：Linux / macOS `sudo relaymesh-agent uninstall --purge`（已是 root 的去掉 `sudo`；用户级安装去掉 `sudo`、加 `--user`，Linux 上会顺带关闭安装时由安装器开启的 linger）；Windows 在管理员 PowerShell 里执行 `relaymesh-agent uninstall --purge`（用户级安装加 `--user`；以最高权限安装的同样需要管理员 PowerShell）。设备离线、Agent 较旧、前台或临时运行、macOS 时只能用这个办法，删除对话框会如实说明并给出命令。

无论哪种办法，`--purge` 只删除服务、身份、守护进程的状态文件与已信任服务器记录，**不会删除** Agent 数据目录下的 `records/`（终端内容记录）与 `runs/`（模型运行输出）；数据目录只在清空时才会一并移除。卸载之后也没有进程再按 §2 的保留期限滚动清理它们——需要清除时，请在设备上手动删除这两个目录。

## 2. 数据放在哪里

核心原则：**终端上显示的内容与模型运行的完整输出只留在被控主机上，RelayMesh 服务端的数据库里没有这些内容。**

| 数据 | 存放位置 | 保留 | 谁能读取 |
|---|---|---|---|
| 人工终端的显示内容（PTY 输出流，含 Shell 对键入的回显） | 被控主机 Agent 数据目录下的 `records/`（文件权限 0600，分段并压缩） | 单会话默认 64 MiB、单主机默认 512 MiB、会话结束后默认 30 天，超出自动滚动清理并留下缺口标记；磁盘剩余空间低于 1 GiB 时暂停录制 | 先在 Web 解锁（输入密码）的管理员，每次查看与下载都写入审计 |
| 模型运行的完整输出（stdout / stderr） | 被控主机 Agent 数据目录下的 `runs/` | 每路前 8 MiB 完整保留，之后只滚动保留最近 256 KiB；运行结束后默认 7 天；受总量配额限制 | 管理员（解锁后）；持令牌的模型通过 `terminal_run` 分页读取自己那次运行的输出 |
| 模型运行的元数据 | 服务端数据库 `terminal_runs` | 默认 30 天后清理 | 管理员 |
| 其中的命令文本 | 同上，已做脱敏 | 同上 | 管理员 |
| 其中的输出预览 | 同上，只有头 4 KiB 与尾 2 KiB（合并 stdout / stderr） | 同上 | 管理员；未解锁时只显示预览 |
| 终端会话的名称、起止时间、结束原因、记录统计 | 服务端数据库 `terminal_sessions` | 随会话记录 | 管理员 |
| 审计日志（谁在什么时候对哪台主机做了什么，被拒绝的越权尝试也记） | 服务端数据库 | 保留最近 2 万条，每天修剪一次 | 管理员 |
| SSH 主机上命令的完整输出 | 远端主机上的 `~/.relaymesh/runs/<运行 ID>`（权限 0700），不回传服务端 | 7 天 | 该 SSH 账户 |
| SSH 主机的登录凭据（服务端直连） | 服务端数据库，用 `RELAYMESH_SSH_SECRET_KEY` 加密（AES-256-GCM，绑定机器码） | 直到删除主机 | 密钥不在数据库里，请与数据库备份分开保管；未设置或过弱时直连后端关闭 |
| SSH 主机的登录凭据（经网关接入） | **只在网关**：网关 Agent 数据目录下的 `ssh-gateway/credentials.json`，AES-256-GCM 密封（绑定机器码），密封密钥是同目录的 `key` 文件（0600）或环境变量 `RELAYMESH_AGENT_SSH_CRED_KEY`；服务端数据库里没有任何副本 | 直到删除主机（或改接别的网关） | 能读到网关数据目录（含密钥）的人；备份数据目录时请连同密钥一并保管，或把密钥外置分开存放 |
| 经网关打开的 SSH 终端的显示内容 | 网关主机 Agent 数据目录下的 `records/`（规则同人工终端；无痕会话不记录） | 同上 | 同上；会话名（默认取主机备注或 `用户@地址`）、起止时间在服务端 `terminal_sessions`，`shell` 记为 `ssh` |
| Hub 直连的 SSH 终端的显示内容 | 只在服务端内存里（每个会话一块 1 MiB 的环形缓冲，用于刷新 / 重连后的回放），**不落盘、不记录**；服务端重启、总闸关闭、停用 / 删除主机即消失 | 会话在世期间；退出后保留 1 小时供回看状态 | 已解锁的管理员；会话本身不入库（谁在何时打开 / 结束了会话仍写入审计日志） |
| 经 `terminal_files` 传输的文件内容 | 只流经服务端内存，不落盘、不进数据库 | 无 | 持有一次性下载地址的一方，120 秒内一次 |

### 2.1 「记录的是终端上显示的内容」意味着什么

- 记录的是**主机终端输出的字节流**：你键入的命令因为 Shell 会回显，所以会出现在记录里；**不单独保存键入的字节**。
- 不回显的输入不会被记录：`sudo` 的密码提示符、`ssh` 的口令输入、`read -s` 等，敲进去的内容不会出现在记录里（包括嵌套会话、tmux、容器和 Windows）。
- 但**凡是屏幕上显示出来的都会被记录**：`cat` 一个含密钥的文件、`echo $TOKEN`、程序打印出的密码，都在记录里。需要避免时，请为这个会话选「无痕」（完全不写任何记录文件），或在主机上用 `--no-record` 整机关闭。
- 记录文件只在被控主机本机、只有运行 Agent 的账户可读；Hub 不会把它们拉回服务端。浏览器回放和下载时，内容经服务端转发但不落盘。

### 2.2 你可以怎么控制

- **整机一票否决**：Agent 启动参数 `--no-record`（或 `RELAYMESH_AGENT_NO_RECORD=1`）——这台主机什么都不记录，服务端无法覆盖。
- **单个会话**：新建会话时选「无痕」。
- **服务端总开关**：`RELAYMESH_TERMINAL_RECORD=off`，下发给每台主机的 Agent；服务端只能让记录更严格，不能放宽主机本地的限制。
- **模型执行的一票否决**：Agent 启动参数 `--deny-model-exec`（或 `RELAYMESH_AGENT_DENY_MODEL_EXEC=1`）——这台主机拒绝一切模型执行与文件访问，服务端的任何授权都无法覆盖。
- **按行数限高**（可选，默认不限制）：每个会话在主机上的记录只保留最近 N 行输出，更早的整段丢弃，见 §6.2。
- **临时身份运行**（`run --temp`）：不记录终端内容，也不支持模型执行。

## 3. 从 v1.6.x 升级到 v2.0.0：行为变化清单

1. **MCP 令牌不能再访问 REST / SSE 管理接口**：用 MCP 令牌调用 `/api/v1/*`（含凭据、设置、会话、事件、`auth/sse_ticket` 等）一律返回 `403 mcp_token_forbidden`，没有兼容开关。`/mcp`、网页登录（JWT）和匿名图片路由不受影响。如果你有自己的脚本用 MCP 令牌调用 REST，请改用网页登录得到的 JWT。
2. **凭据库里已有凭据时，`/mcp` 不再接受无法识别的令牌**：以前带一个错误的令牌，请求会落入「开放访问」而照常通过（不带令牌本来就是 401）；现在一律返回 401（只有凭据库里一条凭据也没有、且没有设置环境变量令牌时才是开放访问）。
3. **新建令牌默认不含终端权限**：`tools/list` 里没有任何终端工具；要给模型终端能力，需要在令牌编辑器里选「ExecMesh 模式」或勾选「终端」权限，并为令牌授权主机。已有令牌在升级后终端权限缺省为关闭。
4. **令牌新增字段**：到期时间、来源 IP 白名单、最近使用时间、终端主机白名单与限额、ExecMesh 兼容命名（均为可选；旧令牌行为不变）。
5. **MCP 请求体有了 8 MiB 的上限**，超出返回 413；环境变量令牌改为恒定时间比较。
6. **终端功能的前置条件不变**：仍需设置 Web 密码且 JWT 密钥足够强才会启用；模型执行与文件能力各有独立的服务端开关，默认关闭。
7. **侧栏左上角出现 `RelayMesh | ExecMesh` 切换器**（仅在远程终端可用时）；RelayMesh 模式里的侧栏、排序、筛选和通知行为保持不变；旧地址 `/terminal` 自动跳转到 `/exec`。
8. **交付卡片可带出提交锚点**：`interactive_feedback` 新增可选参数 `commit`（一行：最近一次提交的哈希与摘要，服务端记录时间），界面显示锚点芯片和「期间有新提交」分隔条；恢复胶囊保存时缺省基于最近的锚点，并出现在会话时间线上。不传 `commit` 时回执与以前逐字节一致。
9. **会话阶段收敛为「讨论 / 方案 / 开发」三段**：旧的 `assess`、`verify`、`done` 在所有入口（MCP 的 `phase` 参数、`set_phase`、Web API）自动映射为 `discuss`、`dev`、`dev`，落库与广播统一用新 id；存量工作流的阶段与全局阶段模板在启动时迁移，可重复执行：`assess`→`discuss`、`plan`、`dev` 三条里你改过的文案（标签、描述、提示词逐字段）原样保留，`verify`、`done` 并入 `dev`，这两条的自定义文案不会保留（所以升级前的备份请留着，见 §1.1）。旧版本不认识内置的 `discuss`：回滚后这些工作流仍能正常读写，但回执里可能收不到该阶段的提示词（没改过全局阶段模板时就是如此），把阶段切到旧版认识的 `plan` 或 `dev` 即可恢复。
10. **界面调整**：ExecMesh 终端页顶部的标签条（切换、新建、缩放按钮）已移除——切换与新建会话都在左侧栏；文字大小改用 Ctrl + 滚轮缩放、Ctrl + 0 恢复默认。设置按模块（通用 / RelayMesh / ExecMesh）分类，页签末尾可一键跳转到另一个模块的设置。
11. **新增的能力**：主机的「新模型默认」授权（默认不允许，升级后行为不变）、独立的任务清单（`/work`）、**SSH 网关**（Agent 的标配能力，默认开启：服务端可以借这台主机去连没有 Agent 的 SSH 主机，但只有你在 Web 上登记了目标才会发生任何连接；想限定可达范围用 `--ssh-allow`，想关闭用 `--no-ssh-gateway`）；已登记的 Hub 直连 SSH 主机现在也能在浏览器里开人工终端，两条接入路径的主机管理与授权完全一致。网关与两条路径的细节见下一节。
12. **Agent 升级提醒与一键升级**：主机清单会提醒版本落后的 Agent，并提供升级窗口与命令（见 §1.2）；主机所有者在本机用 `relaymesh-agent web-upgrade on` 允许后，还可以在 Web 上一键升级（有活动会话时先提醒并要求确认，新版本起不来会自动还原）。旧 Agent 不会被自动升级，一键升级默认关闭；「自动升级」有两种模式，都默认关闭、由主机所有者在本机开启、服务端另有总闸：提示模式只提醒、不下载不升级；静默模式由 Agent 自己发起升级，只安装验过发布签名的新版本（发布流程接入签名之前，生产不会真正升级）。

## 4. SSH 网关（经内网跳板接入的 SSH 主机，人和模型都能用）

这一节回答：经网关接入的 SSH 主机怎么运作、能信任到什么程度、凭据和数据放在哪里、出问题时会发生什么。接入页的「SSH 网关」选项（默认勾选）与专用镜像的 compose 示例见 [README](../README.md) 的「SSH 网关」与「作为 SSH 网关运行」。网关和 Agent 是同一个程序，网关是 Agent 默认开启的一项能力（`--no-ssh-gateway` 关闭）。

### 4.1 两条接入路径

一条 SSH 主机记录只有一条接入路径：要么由服务端直连，要么经某个网关。两条路径在**主机管理上完全一致**：同一套主机卡片，同一套「模型访问」授权（模型能不能用，只由主机的「允许模型使用」和令牌上的主机授权决定）；网页上人工打开终端不受限制（当前是单用户模式，没有人工权限设计）。差别只在「谁去连目标」「凭据在谁手里」和「会话住在哪里」。

| | Hub 直连 | 经网关 |
|---|---|---|
| 谁去连目标 | 服务端 | 网关主机上的 Agent / 会话守护进程；服务端永远不会自己去连 |
| 用途 | 人在浏览器里打开交互式终端，也可以让模型执行命令（`terminal_exec` 等） | 同左 |
| 人工终端的会话 | 由**服务端**持有（每台主机最多 8 个、全部直连主机合计最多 32 个）：刷新浏览器、断线重连都能接上并补回输出；**服务端重启、总闸关闭、停用 / 删除主机、改动地址 / 用户时随之结束**；不记录，没有无痕入口；空闲回收默认永久，可设主机「默认生命周期」；退出后保留 1 小时供回看（详见 §4.7） | 由网关的会话守护进程持有：服务端重启不影响，终端记录在网关本机，有无痕入口 |
| 目标需要对谁可达 | 服务端 | 网关 |
| 会话 / 输出在哪里 | 命令的完整输出在目标上的 `~/.relaymesh/runs/` | 终端会话与终端记录在网关本机；模型命令的完整输出同样留在目标的 `~/.relaymesh/runs/` |
| 登录凭据 | 服务端用 `RELAYMESH_SSH_SECRET_KEY` 加密保存，建连时由服务端使用 | **只保存在网关自己的存储里**（密封）；服务端数据库没有任何副本，也不需要 `RELAYMESH_SSH_SECRET_KEY` |
| 主机密钥 | 必须已固定，逐字节比对，对不上不发送任何凭据 | 同左，由网关比对 |
| 目标的系统要求 | 必须是 POSIX 环境（登记时探测，探测不出的拒绝直连，请改走网关） | 任何 SSH 服务端都可以；探测不出 POSIX 环境的目标（如网络设备、Windows OpenSSH）只能当人工终端用，模型调用得到 `ssh_terminal_only` |
| 能否授权给模型 | 可以（与所有主机一样，在「模型访问」里授权） | 同左（目标须是 POSIX 环境） |
| 本机一票否决 | 没有（控制权完全在服务端） | 有：网关的 `--deny-model-exec` 管到经它接入的主机，服务端无法覆盖 |
| 改变接入路径 | — | 在直连与网关之间、或换一个网关时，必须重新填写凭据（凭据不会在服务端与网关之间搬运） |

### 4.2 信任边界

- **网关是 Agent 的标配能力，关闭权在机器主人**：默认开启（与「主机服务」一样不分版本）；Agent 带 `--no-ssh-gateway`（或 `--ssh-gateway=false`、`RELAYMESH_AGENT_SSH_GATEWAY=off`）即关闭，服务端无法替它打开或关闭。开着不等于有连接——只有你在 Web 上登记了目标、核对并固定了主机密钥，网关才会去连它。`--temp` 不提供网关（明确写了 `--temp --ssh-gateway` 会报错）；`--ssh-allow` 只在网关开启时有意义，与 `--no-ssh-gateway` 同时给出会被拒绝启动。因为默认开启，**建议用 `--ssh-allow` 把目标限定在需要的网段 / 主机内**。
- **允许名单只由网关本机决定**：`--ssh-allow`（可重复，或 `RELAYMESH_AGENT_SSH_ALLOW`，逗号分隔）接受网段（`10.0.0.0/8`）、单个 IP、主机名模式（可含 `*`，如 `build-*.lan`）。目标是 IP 时必须落在某个网段 / IP 里；目标是主机名时先按名字模式匹配（**不看它解析到哪里**），否则解析出全部地址、要求每一个都在允许的网段内。名单之外的目标由网关直接拒绝（`ssh_target_denied`），服务端无法覆盖，所以即使服务端被攻陷，也不能把一个设了名单的网关当成任意跳板。没有设名单时不限制目标，启动横幅会提示。
- **凭据只在网关上**：口令 / 私钥只在登记（或重新填写）的那一次请求里经过服务端——服务端不写数据库、不进日志、不留副本，原样交给网关；网关真实登录成功后，用 AES-256-GCM 把凭据密封保存在数据目录的 `ssh-gateway/credentials.json` 里（每一条绑定到那台 SSH 主机的机器码，别的主机的条目解不开）。密封密钥默认是同目录自动生成的 `key` 文件（权限 0600），也可以用环境变量 `RELAYMESH_AGENT_SSH_CRED_KEY`（至少 16 个字符）外置，外置后凭据库文件单独被拷走也无法解开。之后每次建立终端或执行命令，服务端只发送地址、用户与已固定的主机公钥，**登录凭据由网关自己出示**，不进会话信息、终端记录或日志。结果是：服务端被攻陷时拿不到这些凭据，它最多只能让网关去连名单之内的已登记主机；而网关主机本身被攻陷时，同一台机器上的凭据库与密钥文件会一起暴露（外置密钥可以缓解「只拷走凭据库文件」的情形）。请为这类主机使用权限受限的专用账号（最好用密钥），并在目标上限制来源地址；服务端、网关与目标三者的信任关系要按这个事实来设计。
- **模型执行的一票否决**：网关加 `--deny-model-exec`（或 `RELAYMESH_AGENT_DENY_MODEL_EXEC=1`）后，经它接入的主机拒绝一切模型执行（模型在 `terminal_targets` 里看到 `blocked: host_denied`），服务端的任何授权都无法覆盖；人工终端不受影响。界面会在主机卡片上写明这一点。
- **主机密钥**：登记时由网关探测并由你核对指纹后固定；之后每次连接都必须出示同一把密钥，对不上就拒绝，**不向对方发送任何凭据**，也不会自动重新固定（主机页显示「主机密钥不一致」，核对后才能重新启用）。探测是唯一不带凭据、也不要求已固定的操作。

### 4.3 持久性与数据位置

- **会话由网关的会话守护进程持有**：浏览器刷新、服务端重启都不影响正在进行的 SSH 终端，重新打开页面会回放断线期间的输出。装成常驻服务（两个单元）的网关，Agent 被升级、重启甚至 `kill -9` 也不影响会话；用内嵌模式运行的网关（例如专用容器）里，Agent 进程退出，会话就随之结束，所以请让它常驻（`restart: unless-stopped`）。网关主机重启会结束会话，并如实记录原因。
- **终端记录只在网关本机**：规则、配额与保留期与人工终端完全一致（见第 2 节）；无痕会话不记录。服务端数据库只保存会话名、起止时间与统计。
- **网关的数据**：身份（机器码）、终端记录与加密的凭据库都放在数据目录（专用镜像里是 `/data`，示例里是卷 `gateway-data`）。容器重建后机器码和凭据都在，不需要在 Web 上重新启用，也不需要重新填写凭据；卷丢失则相当于一台新主机，要重新走发现与启用，原来经它接入的 SSH 主机需要改接到新网关并重新填写凭据。备份数据目录时凭据库会随之进入备份，请连同密封密钥一并妥善保管，或者用 `RELAYMESH_AGENT_SSH_CRED_KEY` 把密钥分开存放。
- **凭据对账**：网关（重新）就绪时，服务端会把「仍然需要的 SSH 主机」名单发给网关；网关据此回收名单之外的凭据（例如主机在网关离线期间被删除），并回报自己实际持有哪些。网关上没有的主机在界面显示「凭据缺失」，模型得到明确的 `ssh_cred_missing`，管理员在主机页重新填写即可。网关重启（含容器重建）后会重新对账一次。

### 4.4 生命周期与故障时的行为

| 情况 | 行为 |
|---|---|
| 停用 / 删除这台 SSH 主机，或改动它的地址 / 用户 / 网关 | 立即结束它在网关上的全部会话，并写审计（`session_kill`，detail 里带 `ssh_target=<机器码> disabled / deleted / reconfigured`）；只更换凭据不结束会话；网关自己的其它会话不受影响 |
| 删除这台 SSH 主机，或把它改接到别的网关 | 网关上的凭据在该主机没有进行中的运行之后被清除（最多等待 60 秒）；通知不到网关（离线）的，下一次对账时回收 |
| 网关离线 | 经它接入的主机显示「网关不可用」，不能打开新终端，模型执行也会失败（`ssh_gateway_unavailable`）；网关回来后自动恢复。已有会话在有常驻守护进程时继续运行，网关回来后可重新接上 |
| 网关的凭据库丢了 / 这台主机的凭据不在网关上 | 主机显示「凭据缺失」，模型得到 `ssh_cred_missing`；在主机页重新填写凭据即可，地址、备注、授权等设置保留 |
| 删除网关主机 | 仍有 SSH 主机经它接入时被拒绝（`409 gateway_in_use`，界面会先说明）：先删除这些 SSH 主机，或把它们改接到别的网关 |
| 停用网关主机 | 允许；经它接入的 SSH 主机因此无法打开终端，也无法执行命令，对话框会说明影响 |
| 目标不在允许名单内 | 网关拒绝（`ssh_target_denied`）并说明原因，不发送任何凭据；登记新目标与使用已保存的凭据都一样受名单约束 |
| 目标主机密钥与固定值不符 | 拒绝连接，不发送任何凭据，也不自动重新固定 |
| 网关本机开启了 `--deny-model-exec` | 模型执行被拒绝（`host_denied`），主机卡片上提示"网关一票否决了模型执行"；人工终端不受影响 |
| 网关用 `--no-ssh-gateway` 关闭了网关能力，或版本过旧 | 不会出现在「SSH 主机」对话框的网关列表里；已登记的主机显示「网关不可用」。旧版本网关没有凭据库，需要升级 Agent 并重启守护进程（主机清单会提醒升级并提供升级窗口，见 §1.2） |

### 4.5 排查

- 网关列表是空的：网关必须是已启用、在线、非临时身份的 Agent，并且它的会话守护进程就绪、没有被 `--no-ssh-gateway` 关闭（Agent 启动横幅里应有「SSH网关: 已开启」）；版本太旧的 Agent 没有这项能力，主机清单里会有升级提醒。以服务安装的网关改了参数后，要 `relaymesh-agent holder restart`，守护进程才会采用新参数。
- 探测超时或失败：从**网关主机**出发能否到达目标的 SSH 端口，才是关键（服务端到不到无所谓）；先在网关上 `nc -vz <地址> <端口>`。
- 被「不在允许名单内」拒绝：核对 `--ssh-allow` 的写法。名单里写的是主机名模式时，登记的地址也要写成同样的名字；用 IP 登记的目标只会被网段 / IP 条目放行。
- 主机显示「凭据缺失」：网关的数据目录被清理过、换了新的数据卷，或者 `RELAYMESH_AGENT_SSH_CRED_KEY` 外置的密钥被更换（用旧密钥密封的凭据解不开）。后一种情况下旧凭据**不会被删除**：把密钥改回原值并重启网关，下一次对账后会自动恢复；确实要换密钥，就在主机页逐台重新填写凭据（新的会用新密钥密封）。
- 数据卷是宿主机目录时容器起不来或写不了数据：专用镜像以 uid 10001 运行，请先 `chown -R 10001:10001 <目录>`，或改用命名卷。
- 想确认网关当前持有哪些凭据：在网关的数据目录里看 `ssh-gateway/credentials.json` 的键（就是 SSH 主机的机器码），值是密封后的密文，看不到任何口令。

### 4.6 已验证的 SSH 服务端

下面是在真实服务端上跑过的组合（自动化端到端用例保存在仓库的 `internal/terminal/e2e/` 里，需要 docker 或 Windows 环境，日常 `go test` 不会运行）。网关本身分别运行过在 Linux、Linux 容器（专用镜像）和 Windows 11 上。

| SSH 服务端 | 口令登录 | 私钥登录 | 人工终端 | 模型执行 | 备注 |
|---|---|---|---|---|---|
| OpenSSH（Linux，busybox 环境） | 通过 | 通过 | 通过 | 通过（含输出分页、超时、取消） | 远端运行脚本在 busybox 上的 `timeout` 超时返回 143 而不是 124，已统一归为「超时」 |
| Dropbear | 通过 | 通过 | 通过 | 通过（同上） | 无 |
| Windows 11 自带的 OpenSSH | 取决于服务端配置（默认 `PasswordAuthentication no`） | 通过 | 通过（cmd.exe） | 不支持：目标不是 POSIX 环境，登记时识别为「只能当人工终端用」，模型调用得到 `ssh_terminal_only` | 管理员组的账号要把公钥放在 `C:\ProgramData\ssh\administrators_authorized_keys` |
| 网络设备（交换机、路由器的厂商 SSH） | 未实测（没有环境，暂缓；后续有环境时补测） | 未实测 | 未实测 | 未实测 | 这类设备的命令行通常不是 POSIX shell，预期与 Windows OpenSSH 相同——只能当人工终端用，且必须经网关接入（服务端直连要求目标是 POSIX 环境）；遇到兼容问题请带上服务端的型号与版本反馈 |

Hub 直连的人工终端（§4.7）在真实 OpenSSH（Alpine 容器，浏览器端到端：`scripts/e2e-terminal/e2e/ssh-hosts.mjs`）与进程内的测试 SSH 服务端（`internal/terminal/localterm_test.go`，含竞态检测）上验证过。

### 4.7 Hub 直连 SSH 主机的人工终端（会话在服务端）

Hub 直连的 SSH 主机和经网关的主机一样可以在浏览器里开人工终端：主机页点「打开终端」，或在侧栏「新建终端」菜单里选这台主机。服务端用已固定的主机密钥和加密保存的凭据去连目标、申请 PTY，窗口尺寸跟随浏览器。它和网关路径的差别全部来自「会话住在服务端」：

| 方面 | 行为 |
|---|---|
| 重连与回放 | 每个会话在服务端有一块 1 MiB 的环形缓冲，并跟踪终端模式（备用屏、鼠标上报等）。刷新浏览器或断线重连时按偏移续传、补回断线期间的输出；缓冲不够时如实标注「已截断」，进入备用屏的全屏程序重连后会被重绘 |
| 流控 | 任一浏览器未确认的数据超过 256 KiB 时暂停读取远端输出；超过 10 秒仍不确认，只断开这个浏览器（会话不受影响，重连即可） |
| 生命周期 | 空闲回收默认永久；可在主机页设「默认生命周期」，或在单个会话上设（规则与 Agent 主机一致：「空闲」指没有任何浏览器连接、也没有输入）。会话退出后保留 1 小时，供回看状态与退出原因 |
| 数量上限 | 每台主机最多 8 个会话，全部直连主机合计最多 32 个；超出时明确拒绝 |
| 什么时候结束 | 服务端重启；终端总闸关闭；停用 / 删除这台主机；改动它的地址 / 用户 / 接入路径；目标主动断开。**服务端重启不会保留会话**——这是「会话住在服务端」的代价；需要重启也不中断，请经网关接入 |
| 不提供 | 终端记录与回放（会话信息里 `rec` 为 `off`）、无痕入口、文件传输 |
| 谁能用 | 网页上登录并解锁的管理员，不受限制（单用户模式）。模型是否可用另由「允许模型使用」和令牌授权决定，与人工终端互不影响 |

设计取舍：直连路径的价值是「不需要装任何东西、也不需要中转」，所以会话引擎放在服务端；需要持久、记录和无痕的场景用网关。两条路径在主机卡片、授权和审计上保持一致，避免用户需要记住哪条路径"少了什么"。

## 5. 排查：shell 提示符下输入不了中文（部分 Linux 主机）

**现象**：在终端里 `cd` + 中文目录名、`echo 你好` 之类的输入没反应、被改写，或者弹出一串补全；但在 vim、codex、cursor-cli 这类全屏 / 交互程序里中文输入正常。网页上换输入法（微软拼音、搜狗…）不影响结果。

**原因**：这是主机的 locale 问题，不是输入法问题。bash 的行编辑库 readline 在非 UTF-8 的 locale（`C` / `POSIX`）下，会把 UTF-8 汉字的字节当成 Meta 键（M-d、M-8…），而全屏程序自己读原始字节，不经过 readline，所以它们不受影响。常见的触发者是 Debian 安装器：选了中文环境、又不想让文本控制台显示乱码时，它会在 **root 的 `~/.profile`** 里写入

```sh
LANG=C
LANGUAGE=C
```

终端会话是登录 shell，会执行这个文件，于是 `LANG` 又被改回 `C`。用下面的命令可以确认（在出问题的终端里执行）：

```sh
locale charmap        # 期望 UTF-8；出问题时是 ANSI_X3.4-1968
grep -nE 'LANG|LC_' ~/.profile ~/.bash_profile ~/.bashrc /etc/profile /etc/profile.d/* /etc/default/locale 2>/dev/null
```

**新版本怎么处理**：守护进程创建会话时会把字符类别钉在 `LC_CTYPE` 上（LANG、LANGUAGE 仍由你的脚本说了算），登录脚本把 `LANG` 改成 `C` 也不会让 readline 回到 C locale。要让这项修复生效，需要升级 Agent **并重启守护进程**（`relaymesh-agent holder restart`，会结束这台主机现有的会话；主机清单里「守护进程较旧」徽标就是在提醒这件事），重启之后新建的会话才会带上。

**仍然不行时**（脚本里还直接改了 `LC_ALL` / `LC_CTYPE`，或系统根本没有 UTF-8 locale）：

- 删除或注释掉 `~/.profile` 里的 `LANG=C`、`LANGUAGE=C` 两行，或改成 `export LANG=C.UTF-8`（Debian / Ubuntu 自带 `C.UTF-8`）。
- 没有任何 UTF-8 locale 时先生成一个：Debian / Ubuntu 用 `sudo dpkg-reconfigure locales`（勾选 `en_US.UTF-8` 或 `zh_CN.UTF-8`），CentOS / RHEL 用 `localedef -i en_US -f UTF-8 en_US.UTF-8`。
- 只想临时救急：`export LC_ALL=C.UTF-8`。

## 6. 终端显示与记录的两个可选项：固定终端宽度、终端限高

两项都默认关闭，在 ExecMesh 的设置里打开；它们解决的是两个不同的问题，互不依赖。推荐值都还没有定：下面写的「常用值」与「暂定值」只是起点，之后会按 Cursor / Claude Code / Codex 与常用命令行的实际排版、以及记录文件的实际大小再评估。

### 6.1 固定终端宽度（设置 → 终端偏好）

- **解决什么**：终端的列数是主机上伪终端的真实宽度，换行、全屏程序的排版、记录里的每一行都由它决定。默认列数跟着「最近一次上报尺寸的浏览器窗口」走，在手机上看一眼，回到电脑上看到的历史就是按另一个宽度排的。
- **打开之后**：所有设备都把这个终端报告成同一个列数（40–400，常用 80 / 100 / 120 / 132 / 160 / 200，第一次打开填入暂定的 120）。窗口放得下就用你在「终端字号」里设置的字号；放不下（窄窗口、手机）就自动缩小字号，直到刚好放下——最小 4 px、每次 0.5 px；终端右下角显示「固定 N 列 · X px」，字号低于 7 px 时提示偏小，缩到最小仍放不下才出现横向滚动条。字号在不同设备上各自取整到设备像素，所以同一个列数在不同屏幕上字号不同，排版宽度相同。
- **行数仍然跟随窗口**：只固定列数；终端高度仍是最近一次上报的设备的行数（全屏程序在设备切换时会按新的高度重绘）。
- **保存位置与生效范围**：保存在服务端（`system_settings` 的 `terminal_prefs`）、所有设备共用，登录即可修改（只改浏览器上报的尺寸，不涉及主机上的数据）；别的设备改了，已打开的终端在约 15 秒内（状态轮询）跟随。「终端字号」等其余偏好仍只保存在各自的浏览器里，设置页的每一项都标注了生效范围。
- **已知限制**：窗口比 N 列宽时，终端靠左、右边留白，滚动条贴着容器边缘；手机在 1 倍像素密度的屏幕上 120 列的字号只有 5 px 左右（真实手机是 2~3 倍密度，实际显示更清晰）。

### 6.2 终端限高（设置 → 记录与保留）

- **解决什么**：一直在刷输出的长会话，其记录会增长到字节配额（默认每会话 64 MiB）才开始滚动丢弃。设了行数上限后，记录按行数更早地滚动，上下文存储不会无限膨胀。主机上另外两处存储本来就有界：回放缓冲每会话 1 MiB，浏览器里的回滚行数有自己的上限。
- **语义**：每个会话的记录**至少保留最近 N 行**输出（按输出里的换行符统计，范围 5,000–10,000,000），更早的内容以分段为单位整段丢弃，所以设置之后写入的内容，保留的行数在 N 到 N 多出约一成之间。设置之前就已经写下的较大分段（最大 1 MiB）要等新增输出满 N 行之后才会被丢弃，因此刚设置或刚调小时保留的行数会暂时多一些，随后新增约 2×N 行输出即回到稳态。
- **与其他限制的关系**：与字节配额、保留天数互相独立，哪个先到就先按哪个丢；服务端的设置与主机本机的 `--record-session-lines` 取更严的一个（服务端只能让它更严格）；整机 `--no-record` 与「无痕」会话仍然完全不记录。
- **谁受影响**：运行中的会话（立即生效：已封存的旧分段当场丢弃）与之后新建的会话；已结束会话的记录不受影响，仍按保留期清理。丢掉的内容无法恢复，所以修改需要刚刚重新输入过密码、写入审计事件 `record_policy`（`max_lines=N`），从「不限制」收紧或把上限调小时还要二次确认；放宽或取消上限不会丢任何内容。
- **需要新版守护进程**：行数上限在会话守护进程里执行。守护进程每次启动会声明能力 `rec_lines`；旧守护进程（Agent 升级不会重启它）仍只按字节配额滚动，设置页会提示在线主机里有几台尚未生效。需要时在该主机上执行 `relaymesh-agent holder restart`（会结束其中的会话和模型正在运行的命令，先确认）或 `holder restart --drain`（等运行中的会话与模型命令自然结束后再重启）。
- **不要和「读取记录」混淆**：丢弃发生在写入时，已经丢掉的部分在界面里与字节配额滚动的表现相同：往上翻到记录的开头会看到「从此处开始，更早内容已按配额清理」。

## 7. 模型执行的长任务：超时、等待与输出

模型用 `terminal_exec`（兼容命名下是 `exec` / `exec_start`）在主机上跑命令。时间与输出有几条硬规则，工具说明里也对模型写明了：

- **运行上限 `timeout_seconds`**：默认 120 秒（兼容命名的 `exec_start` 默认 3600 秒），最长 **604800 秒（7 天）**。超过上限的值会被收到 7 天，并在结果的 `adjusted` 里写明（以前是悄悄收的）；令牌上单独设置的运行时间限额更严时以令牌为准，同样写进 `adjusted`。负数直接被拒绝。
- **等待时间 `wait_seconds` 与运行上限无关**：它只决定这一次调用最多阻塞多久（默认 30 秒，最长 120 秒，超过同样会写进 `adjusted`）。命令没跑完时调用返回 `state=running` 和 `run_id`，命令继续在主机上运行；模型凭 `run_id` 用 `terminal_run status`（每次最多再等 120 秒）查询，用 `terminal_run cancel` 取消。所以「跑 7 天的任务」是：把 `timeout_seconds` 设成需要的上限，拿到 `run_id` 后隔一段时间查询一次，而不是让一次调用等 7 天。
- **输出的保存与读取**：每一路（stdout / stderr）在主机上前 8 MiB 完整保留，之后只滚动保留最近 256 KiB，中间被丢掉的部分只记字节数；总量受主机配额限制，运行结束后默认保留 7 天。一次调用内联返回的是开头（默认 64 KiB、最多 256 KiB，由 `max_output_bytes` 决定）加 4 KiB 的末尾；其余用 `terminal_run output` 按 `offset` / `limit` 分页读取，页里的 `next_offset`、`eof`、`gap` 会指出读到哪里、有没有读完、中间有没有被丢弃的缺口。输出特别大的任务，建议让命令自己写日志文件（例如 `make > /tmp/build.log 2>&1`），再用 `tail -n 200`、`grep` 这样的短命令读取需要的部分，不要指望从捕获的输出里翻到被丢弃的中间部分。
- **什么会让运行中的命令中断**：服务端重启、Agent 升级都不影响它（命令由会话守护进程持有，服务端重启后与主机对账）。会让它结束的是：会话守护进程被重启（`holder restart` 不带 `--drain`，命令以「已取消、原因 holder_stopped」结束）、主机重启或守护进程崩溃（对账后标为 `lost`），以及管理员「暂停模型」、令牌被停用 / 删除等治理动作。需要换新版守护进程时用 `holder restart --drain`，它会等模型命令一起跑完（见 §1.2）。

## 8. 终端启动器（会话页头的「终端」按钮）

会话页头「任务」按钮左边的「终端」按钮，用来一键在某台主机的某个目录里启动一个固定命令（典型用法：在项目目录里启动 Cursor CLI），并就地在弹窗里使用这个终端。

### 8.1 预设

- 预设 = 名字 + 主机 + 目录 + 启动命令。预设存在服务端（设置键 `terminal_launchers`，最多 20 条）；名字不分大小写、不能重复，目录必须是完整路径，命令必须是单行。
- 预设有两种类型：**终端预设**（默认，点「启动」打开一个终端，上面这些说的就是它）和**非交互续聊预设**（点「运行」，不开终端，见 §8.7）。类型在新建时选定，之后不能改（要换类型请新建一条）。
- **新建、修改、删除预设需要解锁**：预设决定「点下去会在主机上运行什么」，权限等同于「能在终端里敲命令」。
- **审计只记预设编号与主机，不记命令内容**（命令里可能带令牌）。命令里也不要直接写密钥：命令会出现在进程列表里，改用环境变量或配置文件。

### 8.2 点下去之后发生什么

- 启动用的是 ExecMesh「新建会话」的同一套接口：它在 ExecMesh 里就是一个普通的人工交互式终端，关掉弹窗只是断开，会话继续运行。
- 命令由浏览器在提示符出现后「像人一样敲」，**每个会话只敲一次**（输出安静 350 毫秒，最多等 4 秒）。这不改变会话协议，对任何版本的 Agent 都一样。
- 配了目录时，会先「进入目录」再运行命令，写法按主机的 shell 来：Linux / macOS 是 `cd -- '<目录>' && <命令>`；Windows 上是 PowerShell 的 `Set-Location -LiteralPath '<目录>' -ErrorAction Stop; <命令>`（cmd 是 `cd /d "<目录>" && <命令>`）。目录不存在时命令**不会执行**（主机对找不到的目录会静默回落到默认目录，对会改文件的程序比报错更糟）。`~` 在 Linux / macOS 上留给 shell 展开，在 Windows 上用主机上报的家目录换成绝对路径。各平台的差异与验证程度见 §8.10。
- 「继续」按**主机 + 会话名**认出以前启动的会话，所以服务端会把预设名规整到与会话名完全一致（折叠空白，拒绝零宽与方向控制字符）。

### 8.3 防误触

- 终端里按 Esc 归程序（Cursor CLI 用它打断当前这一步），点弹窗外面不会关闭弹窗；预设表单里点外面也不关。
- 结束会话与删除预设都要点两次才生效。

### 8.4 限制

- 只支持 Agent 主机；经 SSH 网关的主机暂不支持。终端预设在 Windows 主机上也能用（PowerShell / cmd），非交互续聊预设暂不支持 Windows 主机；差异见 §8.10。
- Cursor CLI 新版的命令叫 `agent`，旧版叫 `cursor-agent`，按主机上实际装的写。
- 启动器本身只负责「启动」。会话意外结束或停摆之后，只有监测、通知和「你点一下」的唤醒（§8.5）；没有自动重启、自动唤醒。

### 8.5 会话守护（监测、通知、一键唤醒）

给预设开「会话守护」后，Hub 每分钟判断一次这个预设的会话是不是出了问题，并在启动器里给出处理入口。**只做监测、通知，以及你点一下才唤醒；不会自动唤醒、不会自动重启。**

- **配置**（预设表单里的「会话守护」，保存同样需要解锁）：
  - **命令退出即结束会话**（可选，默认关闭）：启动时用 `exec` 包装命令，CLI 一退出 shell 随之退出，退出码准确，守护能立刻判「意外结束」。命令不能含 shell 运算符、复合语句或内建命令；带前置环境变量时改写成 `exec env …`。
  - 监测开关；
  - 工作流编号：这个会话里的智能体使用的 RelayMesh 工作流。不填只能发现「会话意外结束」，分不清「它在合法地等你回复」和「它停摆了」；
  - 停摆判定分钟数（默认 30，范围 5～720）；
  - 重新拉起命令（可含 `{chat_id}`）；
  - 唤醒提示词（单行，最多 300 字，可用 `%n`、`%max`、`%reason`、`%workflow`；留空用内置默认）。提示词里不能有 shell 特殊字符，因为万一 Cursor CLI 已经退出，这句话会落在普通命令行里。
- **唤醒许可（任务全部完成）**：
  - 智能体收尾前可调用 `workflow_context(action:"wake_permit", permit:0)`（可选 `note`）；你也可在启动器清单里点「标记完成」（需解锁）。
  - 标记有效期间，本会话若按原规则会判为意外结束、停摆、已结束或空闲，则显示 **「已完成」**、不推送、不出红点；在干活 / 等你回复 / 有人连着不受影响。
  - **一次性**：本该触发告警的那一次会消费标记并恢复许可为 1（同一次事件仍显示「已完成」、不重复推送）；有新的待处理的事、手动唤醒、取消标记或超过 24 小时也会失效。
  - 绑定启用守护的预设时，MCP 回执头会多一行 `guard:` 提示上述用法。
- **怎么判断**（按优先级）：
  1. 会话已经没了：看结束原因与退出码——手动结束、空闲回收、策略结束、命令正常退出算「已结束」；异常退出、被信号终止、主机重启、守护进程停止或崩溃、会话从列表里凭空消失算「意外结束」；12 小时之前的意外结束降为「较早之前结束」。
  2. 有人正连着这个会话：不打扰。
  3. 智能体在 RelayMesh 里合法地等你回复（有待回复的会话、没超期）：不算停摆。
  4. 编辑器 hook 汇报：一轮对话以 `error` 收尾、5 分钟内没有新动静，算停摆（出错中断）。
  5. 超过「停摆判定」时间没有任何活动（工具调用、收尾、RelayMesh 交互），并且有待处理的事（没读的回复 / 追加指令、进行中的任务），算停摆（长时间无活动）。
- **通知**：「意外结束」和「停摆」是需要处理的状态。会话页顶栏「终端」按钮上亮红点（悬停写明是哪个预设、怎么了），启动器清单里有状态行；配了 ntfy 时推送一条——同一次事件只推一次，之后最多每 6 小时再提醒一次、最多 2 次；你已经唤醒过就不再提醒。
- **唤醒**（清单里的按钮，需要解锁；Hub 只生成并登记这次唤醒，真正「敲」的是浏览器，等于你在键盘上敲）：
  - **唤醒**（会话还活着）：把提示词输入到会话里。**文字与回车是两次分开的输入，相隔 0.4 秒**——Cursor CLI 这类 TUI 会把一次性送进去的整串当成粘贴，回车就成了换行而不是发送。
  - **重新拉起**（会话已结束）：在预设的目录里新开会话，运行重新拉起命令（有 `{chat_id}` 且 hook 汇报过对话编号时接着原来的对话，否则用预设自己的命令开新对话），并把提示词作为命令**最后一个**单引号参数带上。Windows 主机、或命令带管道 / 重定向时不追加，改为提示「复制提示词」。
  - **Windows 与 exec 启动**：Linux / macOS 上开启「命令退出即结束会话」时，启动行会先 `cd -- '<目录>'` 再 `exec …`。Windows 主机**不会**自动拼 `cd`（路径与 shell 语义不同）；启动行仅为 `exec <命令>` 或 `exec env …`，工作目录依赖 Agent 为该会话设置的默认目录。若必须在特定目录下跑，请把 `cd` / `Set-Location` 写进命令本身，或改用 Linux / macOS 主机做 exec 包装。
  - 提示词开头固定是「【系统唤醒 第几次/上限 · 原因：…】」，后面是你配置的正文（默认正文让智能体先读收件箱、查看最近会话与任务、核对 git 状态，不重复已完成的步骤，不可逆操作先确认）。
  - 审计只记 `guard_wake`（预设编号、方式、第几次），**不记提示词与命令**。
- **次数与效果**：滚动 24 小时内参考上限 3 次。手动唤醒不会被拦，但超过上限、会话看起来没出问题（在干活 / 在等你回复 / 有人连着）、或最近连续 2 次没有效果时，会先在行内问你一次。唤醒后 10 分钟内智能体有了新动静记为「有效果」，否则记为「没有动静」——多半不是它需要被叫醒，而是 Cursor CLI 已经退出、网络不通或额度用完。
- **编辑器 hook**：停摆判断里的第 4 条依赖 Cursor hook（Go 二进制 `relaymesh-hook`，安装见 `docs/inbox.md`）的上报——事件种类、对话编号、一轮对话的结束状态（`completed` / `aborted` / `error`），不转发任何对话内容。旧版 hook（包括已移除的 Python 版）没有这些，需要按 `docs/inbox.md` 重新安装；没装时守护只能发现「会话意外结束」和第 5 条。
- **回滚兼容**：守护配置存在预设的 `guard` 字段里，运行状态存在设置键 `terminal_guard_state`。回滚到更旧的 Hub 后，在那边重新保存预设会丢掉 `guard`；反馈会话的 `responded_at` 列是新增的，旧版本可以照常打开数据库。
- **已知局限**：
  - 未开启「命令退出即结束会话」时，启动命令是输入到 shell 里运行的：Cursor CLI 自己退出（崩溃）后，会话仍停在 shell 提示符上，会话本身没有结束，所以发现不了「意外结束」，只能靠第 5 条（需要工作流编号）在 30 分钟左右后判为停摆。开启 exec 包装可消除这一盲区。
  - 「文字与回车分开输入」已用假的原始模式 TUI 做过端到端验证（`scripts/e2e-terminal/e2e/terminal-guard.mjs`）；在 Cursor CLI 真实界面里是否同样有效，需要在一个低风险会话里试一次。

### 8.6 非交互唤醒（会话守护预设里的可选项）

会话**已经结束**、又需要叫醒它时，如果不想开终端，可以在预设的「会话守护」里打开「非交互唤醒」：清单里会多一个「非交互唤醒」按钮，点它并确认后，Hub 经这台主机的执行通道运行一次

```
agent -p --resume <对话编号> --approve-mcps --trust [--force] --workspace <目录> --output-format stream-json '<唤醒词>'
```

它不开终端、没有 TUI，结束后在聊天里记一条系统行。边界：

- 默认关闭，逐预设开启；改预设要先解锁，所以放宽权限不会被悄悄改掉。
- 只在你点按钮并确认时发生（需要刚解锁）；没有任何自动触发，自动唤醒仍未授权。
- 复用模型执行的全部闸门：总开关、暂停、主机的「模型访问」、主机的执行模式（「需批准」模式下这次运行会停在待批准，要在 ExecMesh 里批准）。
- **权限姿态**：`allowlist`（默认，不带 `--force`，只能做 Cursor CLI 配置里 `permissions.allow` 放行的事）或 `force`（放开全部命令）。`--approve-mcps` 只批准 MCP 服务器、不批准工具调用，所以要让它读写 RelayMesh，需要在 CLI 配置的 `permissions.allow` 里写 `Mcp(<服务器名>:*)`。
- 与键入唤醒共用「24 小时 3 次」，这里是**硬上限**（无人值守的模型调用有成本）；被拒绝的请求不占名额。
- 只用于会话已经结束之后：会话还活着时再续聊同一个对话会和它打架。
- 审计只记预设编号与姿态，不记唤醒词与命令；聊天里的系统行也不含。

**默认唤醒词会补上一段非交互运行的说明（#125）**：这种运行结束后没有人在终端里看输出，而「说明原因后等待」在这里恰恰等于结束本次运行，不说清楚智能体会一句话不说就悄悄退出。所以默认唤醒词后面会追加「这是一次非交互运行……结果必须发到 RelayMesh：恢复现场后先用 `interactive_feedback` 发一条进度通知，结束前再发一条说明结果；这里的等待就是结束本次运行」。你自己写的提示词不加（那是你自己的话），键入终端的唤醒也不加（那里它会一直活着）。

**空转提示**：运行成功结束（退出码 0），但从开始到结束这段时间里智能体没有向这个工作流发过任何消息（汇报 / 进度通知、提问 / 计划卡、任务进展都算；运行结束之后别的会话发的不算），聊天里的结束行会追加「空转退出」的说明，并指向 ExecMesh 的运行记录。读不到消息记录时宁可不提示，也不凭残缺的事实说它什么都没做。没有配工作流的预设没法判断，不提示。

### 8.7 非交互续聊预设（`kind: headless`，#126）

把手敲的 `agent -p --resume <对话> --model <模型> … '<提示词>'` 包成启动页里的预设：新建时选「非交互续聊」，点「运行」，Hub 经这台主机的执行通道运行一次（不开终端、没有 TUI），结果显示在预设清单里。它和 §8.6 是同一条通道、同一套闸门，区别是：它是一条**独立的预设**（不依附会话守护），可以固定模型、对话与提示词。

- **选项**（保存同样需要解锁）：
  - 目录：主机上的绝对路径，运行时作为 `--workspace`；
  - 命令：默认 `agent`，旧版叫 `cursor-agent`；只允许字母、数字和 `_ . / ~ + -`（可以写绝对路径，比如 `/root/.local/bin/agent`）。**不要把它留成别的主机上才有的名字**：主机找不到就运行失败；
  - 工作流编号：用来找到智能体最近的对话（hook 汇报的对话编号）；也可以直接固定一个对话编号，二者至少填一个；
  - 模型：可选，最长 64 个字，只能含字母、数字和 `. _ : / + -` 并以字母或数字开头（`claude-sonnet-5-5-max`、`gpt-5.2` 这类）；不填用 CLI 默认模型；
  - 权限姿态：`allowlist`（默认，不带 `--force`）或 `force`（放开全部命令），含义同 §8.6；
  - 最长运行时间（`max_run_minutes`，分钟，#141）：可选，表单里是「数字 + 单位（分钟 / 小时 / 天）」，不填 = 平台单次运行上限 7 天，填了就收进 1 分钟到 7 天（API 里超过 7 天的值会被收进 7 天，负数被拒绝）。到点主机强制结束这次运行；见下面的「超时」；
  - 异常退出时自动续跑（`auto_resume`，#151）：可选，默认关闭；打开后，可重试的异常退出会自动再续聊一次，见下面的「异常退出自动续跑」；
  - 续跑成功的判定时长（`auto_resume_ok_minutes`，#172）：可选，只在开着自动续跑时有意义；不填 = 10 分钟，可填 1 分钟到 1 天（1440）；续跑出来的运行连续跑满这么久就算续跑成功，累计的次数清零，见「预算与熔断」；
  - 提示词：可选，单行，`%workflow` 换成工作流编号；不填用内置默认（和 §8.6 一样会补上「结果必须发到 RelayMesh」，并且**运行时会再补一句本次的最长运行时间**，让智能体在到点前先汇报进度；自定义提示词不会被加任何东西）。
- **命令只由这些字段拼出**，每个动态部分都用单引号包起来——预设不能写任意命令。
- **「运行」之前的检查**，任何一项不满足都不会产生运行记录：主机在线、不是 Windows、模型执行闸门放行；上一次运行已经结束（否则 `run_active`，到 ExecMesh 里可以取消它）；要接着的对话**不在运行**（工作中且没卡住、在等你回答、在等批准时拒绝，`conversation_live`——原来的进程还活着，再续聊会打架；卡住、已结束、掉线都放行，空闲只提示）；找不到对话编号时拒绝（`no_conversation`）。
- **结果**：清单里显示最近一次运行的状态（运行中 / 已结束 · 成功 / 失败 / 超时 / 已取消 / 待批准……）、用时、最后一条回复（取自 stream-json 末尾的 `result`，没有结构化回复时取输出末行；已脱敏、压成一行、限长）和「运行记录」链接（跳到 ExecMesh 的线程页看完整输出）；成功但智能体没向 RelayMesh 说过话时，状态写「已结束 · 空转退出」并给出补充说明（口径同 §8.6）。聊天里先后有「你手动运行了预设…」与「非交互续聊已结束：…」两条系统行，**不含提示词与命令**。
- **默认只在你点「运行」时发生**（需要刚刚解锁）；唯一的自动触发是你在预设里打开的「异常退出时自动续跑」（#151，默认关闭，见下）。审计记预设编号、运行编号与权限姿态，不记提示词与命令。
- **超时（#113 / #141）**：一次运行默认最长 7 天（平台单次运行上限；cursor-cli 续聊是一个会话，原先固定 30 分钟会在到点时把正在干活的会话强制结束），预设里可以逐个设更短的「最长运行时间」。这个值就是这次运行的超时：下发给主机，也写进运行记录（`timeout_sec`）。到点主机强制结束运行，运行状态是 `timeout`，界面与聊天系统行写「**达到运行时长上限**（30 分钟）」而不是含糊的「超时」，并说明对话本身没有结束、可以接着聊。
  - **「还在跑」的兜底阈值按每次运行自己的超时算**：运行记录停在「进行中」超过它自己的超时加 5 分钟（从运行真正开始算；待批准的从创建算）就不再算「还在跑」，免得异常残留的记录挡住下一次运行；一条 30 分钟的运行残留后不会像 7 天的那样挡一周。「需批准」的主机上，运行要先等批准（最长 10 分钟），批准之后才开始计超时，所以起点是：运行真正开始的时刻；已批准、主机还没报「已开始」的，从批准那刻算；还在等批准的，从创建算并再加上等批准的 10 分钟（否则超时只有 1 分钟的运行会在批准之前就被当成残留）。没有超时值的旧记录用 7 天加 5 分钟的兜底值。运行监视的寿命同理：运行自己的超时加余量（等批准最长 10 分钟 + 到点后收尾 5 分钟），不超过全局上限。
  - **残留记录的收尾**：运行结束时（正常退出、被取消、守护进程上报结束）记录照常收尾，不用等到阈值；阈值只是兜底。Agent 掉线重连后会与主机上还在跑的运行对账：Hub 记着在跑、主机清单里却没有的，宽限 15 秒仍没等到结束事件就收尾成「状态丢失」（`lost` / `not_on_host`），预设随即可以再运行；Hub 重启后进行中的记录会被接回（待批准的作废）、等主机重连后同样对账；超过「自身超时 + 10 分钟」仍未报告的记录收尾成 `lost` / `overdue`。
- **异常退出自动续跑（#151，默认关闭）**：预设里勾选「异常退出时自动续跑」（`run.auto_resume`）后，这个预设发起的运行以**可重试的异常退出**结束时，Hub 在退避之后自动再运行一次——同一套闸门、同一条命令，与你手动点「运行」没有区别，只是由系统发起。它是无人值守的模型调用，会产生用量，所以默认关闭、有预算与熔断。只适用于预设发起的运行；会话页「运行」、§8.6 的非交互唤醒、你在终端里手敲的都不受影响。
  - **怎么分辨异常退出**（`internal/terminal/run_exit.go`，只用运行记录里已有的信息，不加新的观测）：被你取消、到运行时长上限、没跑起来、状态丢失都**不算**出事，也不重试；退出码 0 是成功；失败的运行再看输出末尾（从后往前最多 40 个非空行里最靠后的一行）有没有 Cursor CLI 自己打印的错误行 `<类别>: [<Connect 错误码>] <说明>`（例如 `RetriableError: [resource_exhausted] Error`，见 D-260）：`RetriableError` = 可重试；`ActionRequiredError`（要你处理：登录、额度、确认……）与 `NonRetriableError` 都**不重试**；被 SIGKILL / SIGSEGV / SIGABRT / SIGBUS / SIGILL / SIGFPE 终止的算崩溃，可重试（SIGTERM / SIGINT 这类像是有意结束的不重试）；认不出原因的失败**不重试**——宁可不做，也不在不明原因上反复烧模型。引号里的 JSON 或离末尾很远的同名文字不会被当成错误行。
  - **预算与熔断**：同一预设 24 小时内最多自动续跑 3 次；退避按这 24 小时内已经续跑的次数取，默认 5 分钟 → 20 分钟 → 1 小时；自动续跑出来的运行如果没跑满判定时长（默认 10 分钟）就又失败，算「没有进展」，**连续 2 次**就熔断。预算用完或熔断就不再排期，并通知你（Web 通知 / ntfy「「X」不再自动续跑」；只有「放弃」才推，计划与开跑只写聊天系统行，运行结束本身的推送沿用你已有的运行通知设置）。
  - **续跑成功清零（#172）**：续跑出来的运行**连续跑满判定时长**（预设里的「续跑成功的判定时长」，默认 10 分钟；与上面「没有进展」是同一条界线）就算这次续跑**成功**：24 小时内累计的续跑次数与退避**从这次成功之后重新算**——之后再出事是新的一轮，仍从第 1 次（5 分钟）开始，不会被成功之前的次数拖到「已续跑 3 次」而停下。成功是在运行还在跑的时候就认定的（守护循环每个周期检查一次，不必等它结束，它可能一直跑下去），也可以在运行结束时认定（运行结束上报的用时算数）；认定时聊天里写一行系统行（「预设「X」自动续跑出来的运行已经连续跑满 N 分钟，算这次续跑成功……」），状态行标「自动续跑 n/3（已成功）」，卡片上写「续跑成功：……次数已清零」。没有跑满判定时长就失败的续跑**照常累计**（24 小时 3 次的上限与连续 2 次熔断仍是它们的安全网）；你手动运行出来的不是续跑，不参与判定。判定时长原样存取（`run.auto_resume_ok_minutes`，不填 = 10 分钟，超过 1 天收进 1 天，负数拒绝）。
  - **到点前后的核对**（守护循环每分钟看一次排期，到点前什么都不做）：预设被删、改成别的类型、关掉了自动续跑 → 作废；你已经手动重新运行过（手动运行一次就会取代这次计划）→ 作废；排定时间已经过去超过 2 小时（Hub 停了很久、主机一直离线）→ 作废；主机还没回来 → 继续等；上一次运行还在进行、或对话还在工作 / 在等你回答 → 作废（有人接手了，不去打架）；对话在出事之后 2 分钟以上又有新动静 → 作废（同样是有人接手了）；其余检查与手动运行完全一样，不通过就放弃并写明原因。通过后**先占预算名额再提交**（占不到就放弃，一份计划不会开跑两次），提交失败会退还名额。
  - **在哪里看到**：预设清单里最近一次运行的卡片——失败原因（Cursor CLI 自己报的错误类别 + 一句中文 + 你可以怎么办）；排期中显示「将在 N 分钟后自动续跑（第 1/3 次）」和「取消自动续跑」（只需要登录，不需要解锁；你直接点「运行」也会取代计划）；续跑出来的运行在状态行标「自动续跑 n/3」（已经认定成功的标「自动续跑 n/3（已成功）」）；你取消、作废、放弃时写明原因（放弃是错误色）；「没开自动续跑」或「这类失败重试没有用」时也会说清楚为什么没有续跑。聊天里有计划行、开跑行、取消 / 作废行与放弃行（**不含提示词与命令**）；审计记 `launcher_auto_run`（系统发起，`preset=… attempt=n/3`）与 `launcher_auto_stop`（你取消）。预设清单的摘要里，开着自动续跑的预设写「异常退出自动续跑」（判定时长是自定义的另写「（跑满 N 分钟算成功）」）。
  - **状态存放**：守护状态文档（`system_settings` 的 `terminal_guard_state`，每个预设的 `auto_resumes`）；每个预设最多 30 条、保留 7 天，排期中的不受保留期限制。
  - **仅供实验与端到端测试的三个参数**：`RELAYMESH_TERMINAL_GUARD_TICK_SEC`（守护循环的检查间隔，秒，默认 60）、`RELAYMESH_TERMINAL_AUTORESUME_BACKOFF_SEC`（退避，逗号分隔的秒数，默认 `300,1200,3600`）、`RELAYMESH_TERMINAL_AUTORESUME_OK_SEC`（续跑成功的判定时长，秒；设了就压过预设里的值）；生产不要设，用法见 `scripts/e2e-terminal/README.md`。
- **回滚兼容**：预设里的 `kind` / `run` 字段是新增的（`run.max_run_minutes` 同理，没设时不出现）。旧版本不认识它们，这类预设在旧版里没有命令，不要在旧版里重新保存（会丢掉这些字段）；回滚后新版本留下的数据库照常可以打开，旧版只是忽略「最长运行时间」、仍按 7 天运行。`run.auto_resume`（#151）同样是新增的可选字段（关着不出现），守护状态文档里也多了 `auto_resumes`（#172 又给每条登记加了可选的 `settled`）：旧版忽略它们，所以回滚后自动续跑不再发生（排期中的计划随之失效，不会补跑），不会损坏任何数据；`run.auto_resume_ok_minutes`（#172）同理，没设时不出现，旧版忽略。
- **测试**：`scripts/e2e-terminal/e2e/launcher-run.mjs`（预设与运行）、`scripts/e2e-terminal/e2e/auto-resume.mjs`（自动续跑；Hub 要带缩短计时的实验参数，见该目录 README）；单元测试 `internal/terminal/{run_exit,auto_resume}_test.go`、`internal/store/terminal_guard_state_test.go`。预设里的命令必须填**假 agent 的绝对路径**，否则会按 `PATH` 跑到真实的 Cursor CLI。

### 8.8 非交互运行的状态来自运行输出（#129）

经 Hub 的执行通道运行的非交互续聊（§8.6 的非交互唤醒、§8.7 的续聊预设）里，会话状态卡**不再等编辑器 hook 的汇报**，而是直接读这次运行的输出（`--output-format stream-json`，一行一个事件）。原因：`-p` 模式下 hook 很不完整（没有 `stop`、续聊没有 `sessionStart`、只在正常退出时才有 `sessionEnd`），agent 被杀或超时时 hook 什么都不知道；而 stream-json 里每个事件都是确定的。

- **事件怎么翻成状态**：`system/init` 一次运行开始（工作中）；`thinking` 思考；`tool_call` 的 `started` / `completed` 工具开始 / 结束（按 `call_id` 配对；并行的工具调用结束一个后回到仍在途的那个；工具名取 `<种类>ToolCall` 的种类，如 `Shell`、`Read`；结果里是 `error` / `rejected` 之类的键算失败，shell 命令退出码非零仍算工具成功，与 hook 口径一致）；`assistant` 回复；最后的 `result` 这一轮结束（成功 → 空闲；`is_error` 为真或 `subtype` 不是 `success` → 出错）。
- **没有 `result` 就结束的运行**：按运行本身的结局补一个结束——成功退出 → 空闲，被取消 → 已中断，失败 / 超时 / 失联 → 出错。只在这次运行确实碰过这个对话（读到过事件）时才补；一个事件都没有的运行不动状态。
- **状态卡**：多一行「状态来源」（运行输出 / 编辑器 hook / 终端画面），脚注随来源变化；运行结束后空闲态写「空闲 · 本次运行结束（可续聊）」，中断 / 出错写「本次运行被中断 / 出错」——运行结束不等于对话结束，可以接着聊。SSE 的 `agent_state` 事件带 `source` 字段，卡片不用等重取就知道来源。
- **运行权威**：运行期间（以及结束后 10 秒的收尾）这个对话上 hook 的汇报**只记录、不改状态**，事件记录里标 `run_authority`——否则晚到的 `sessionEnd` 之类事件会把还在跑的运行标成结束。权威是 45 秒的租约，监视协程每一轮续租；Hub 异常退出时租约自然过期，不会卡死。收尾结束后 hook 重新生效，来源回到「编辑器 hook」。
- **不会出现「疑似等批准」**：非交互运行没有审批，工具跑得久只是在跑（仍保留 10 分钟 / 60 分钟的超时标记）。
- **延迟**：Agent 推送的实时输出片段只用来「催」监视协程，真正的读取走执行通道的分页读，另有兜底轮询（Agent 主机 2 秒、SSH 主机 5 秒）。实测从输出出现到状态卡变化不到 1 秒。
- **Hub 重启**：仍在进行的运行会重新挂上监视（重放历史输出，只发最后一个信号）；同时最多监视 64 个运行。
- **范围与限制**：只覆盖 Hub 自己发起的运行；你在终端里手敲的 `agent -p …` 不受影响（仍靠 hook / 终端屏幕）。解析器容忍半行、超长行（只看开头）、非 JSON 的纯文本行、不认识的事件、乱序与输出缺口，认不出的当没看见。stream-json 的字段形状来自已知格式，**尚未用生产上的真实运行校验**——第一次真实运行后请看一眼状态卡是否随输出变化。
- **回滚兼容**：新增 `agent_sessions.state_source` 列（可空字符串，旧版本忽略）；SSE 事件多一个 `source` 字段（旧前端忽略）。
- **测试**：`internal/terminal/{streamjson,run_watch}_test.go`、`internal/store/agent_run_test.go`、`internal/agentstate/source_test.go`；浏览器 e2e `scripts/e2e-terminal/e2e/run-state.mjs`（预设里的命令必须填假 agent 的绝对路径）。

### 8.9 会话页底部的「运行」按钮与启动器「本项目」（#128 → #140）

#128 起会话页状态卡里有一节「运行」面板，可以不建预设就对这个会话做一次非交互续聊；#140 把它**并进终端预设**：状态卡里不再有运行面板，输入区底部在「有对应的续聊预设、并且这个会话停下来了」时出现一个「运行」按钮，点它运行的就是那个预设（§8.7：同一条通道、同一套闸门、同一个命令拼装器）。要先有预设：没有时启动器里会给一张预填好的「为这个会话创建续聊预设」建议卡。

- **会话与预设怎么对应**（服务端判定，浏览器只显示结论；比「目录 + 主机」多一条「跟着这个会话」）：一个续聊预设对应一个会话，当且仅当同时满足——
  - 主机：预设的主机在这个会话的主机名所匹配的主机集合里（口径与 `terminal_exec` 解析 target 相同：先看机器码，再看显示名——有备注用备注、没有备注用主机名，最后才把主机自报的主机名当别名；不区分大小写；同名多台时预设钉在其中一台上就算）。会话没上报主机名（或上报的只是 store 补的占位名 `hosts`）时不按主机过滤；
  - 目录：预设的目录与会话身份里的项目目录严格相等（`path.Clean` 之后，不做前缀匹配）；
  - 跟着这个会话：预设的 `run.workflow_id` 等于会话的工作流，或固定的 `conversation_id` 等于会话的对话编号。同机同目录但跟着别的工作流的预设不算。
- **「运行」按钮什么时候出现**：没有对应预设时不出现；会话正在工作 / 等你回答 / 等批准时不出现（原来的进程还活着，再续聊会打架）；对应的预设都在忙（上一次运行没结束 `run_active`、对话还在运行 `conversation_live`）时不出现。有多个可运行的预设时，确认框里先选一个。预设现在能不能运行由服务端现算（`GET /api/v1/terminal/launchers/for-session?workflow_id=` 给每个预设返回 `can_run` / `busy` / `issues` / `warnings` / 将运行的命令 / 最近一次运行），不能运行的原因（主机离线、Windows 主机、模型执行闸门没放行、缺目录或对话编号……）写在置灰按钮的悬停说明里。
- **点了「运行」**：先弹**二次确认**——写明主机 · 目录 · 对话前 8 位 · 模型 · 权限姿态（`allowlist` 时提示「不带 `--force`，遇到要批准的操作会停住」），可展开看将运行的整行命令；确认后才提交，提交需要刚刚解锁。运行中按钮收起，状态徽标的来源变成「运行输出」（§8.8），结束后按钮回来。
- **检查的先后**：预设运行与预览共用同一个 `inspectLauncher`，错误按「主机 → 上一次运行（`run_active`）→ 对话（`no_conversation` / `conversation_live`）→ 命令」排序。同一个预设正在运行时，对话多半也显示「工作中」，但「上一次运行还没结束」才是更准确的说法，所以再点只会得到 `run_active`。
- **状态徽标**：会话页顶栏的 Agent 状态徽标上直接显示完整信息——状态文字 + 细节（工具名等）+ 来源（运行输出 / 编辑器 hook / 终端画面）+ 用时与 token；窄屏只留圆点和状态文字，来源写在悬停说明里。
- **启动器的「本项目 / 全部」**：从会话页的「终端」按钮打开启动器时，清单分两个标签。「本项目」= 目录等于或在这个会话项目目录之下的预设（会话的主机已知时还按主机过滤）；默认停在「本项目」，除非那里既没有预设、也给不出建议——此时默认「全部」。要定位的预设（从状态卡点「唤醒」进来）不在本项目里时直接看全部。
- **「为这个会话创建续聊预设」建议卡**：只在「本项目」标签、且还没有对应预设时出现，预填名字（`续聊 · <目录末段>`）/ 主机 / 目录 / 工作流编号 / 权限姿态（保守默认 `allowlist`）。主机能唯一确定时可「一键创建」（保存仍需解锁；创建前不会运行任何东西）或「调整后创建」；会话没上报主机名（或是占位名）、有多台同名主机时只给「选主机并创建」。给不出建议时写明原因：上报的主机名在主机清单里对不上（先接入那台机器，或给已接入的主机写一个同名备注）、会话没有目录或目录不是绝对路径、预设已到上限。
- **接口**：`GET /api/v1/terminal/launchers/for-session?workflow_id=` 返回 `{session: view}`（登录即可，只读）；运行走 §8.7 的 `POST /api/v1/terminal/launchers/:id/run`（需解锁，拒绝时 409 `{code, error}`）。#128 的 `POST /api/v1/terminal/session-run/preview`、`GET /api/v1/terminal/session-run/status?workflow_id=`、`POST /api/v1/terminal/session-run` 仍保留给脚本与旧前端，但 Web 不再调用。
- **范围与限制**：同 §8.7——只对命令行（`agent`）里的对话有意义，来自编辑器（IDE）的对话 `agent --resume` 多半找不到；不支持 Windows 主机；手敲的 `agent -p …` 不认（只认预设）。
- **回滚兼容**：没有新增表或列；旧版本没有 `for-session` 接口（404），底部「运行」按钮与建议卡不出现，其余照常。
- **测试**：`internal/terminal/{session_launchers,launcher_run,session_run}_test.go`、`frontend/src/lib/terminal/sessionLaunchers.test.ts`；浏览器 e2e `scripts/e2e-terminal/e2e/session-quick-run.mjs`（预设里的命令必须是假 agent 的绝对路径，脚本里有安全闸，实验 Agent 的 PATH 里也没有真实 Cursor CLI）。

### 8.10 Windows / macOS 主机上的差异（#163）

预设的命令是浏览器在会话提示符出现后「像人一样敲」进主机默认 shell 的，所以**命令本身要按那台主机的 shell 来写**（我们不翻译命令；表单里选了 Windows 主机时会提醒）。主机上报的系统与 shell 决定其余几处的写法：

| 项目 | Linux | macOS | Windows（PowerShell） | Windows（cmd） |
|---|---|---|---|---|
| 默认 shell | 账户 shell，登录方式（`-l`） | 账户 shell（通常是 zsh），登录方式 | 依次选 pwsh、powershell、cmd，守护进程上报选中的那个 | 同左（只有机器上没有 PowerShell 时才会落到 cmd） |
| 目录写法 | `/…`、`~`、`~/…` | 同 Linux | 盘符路径（`C:\work`）、UNC；`~`、`~\x` 用主机上报的家目录展开；`/…` 没有确定含义，表单会提醒 | 同左 |
| 先进入目录 | `cd -- '<目录>' && <命令>` | 同 Linux | `Set-Location -LiteralPath '<目录>' -ErrorAction Stop; <命令>` | `cd /d "<目录>" && <命令>`（目录含 `% " ^ !` 或是 UNC 路径时不拼） |
| 路径里的特殊字符 | 单引号包起来，单引号转义 | 同 Linux | 单引号字面量；PowerShell 把弯引号 `‘ ’ ‚ ‛` 也当单引号，所以这四种都翻倍 | 双引号；含会被 cmd 改写的字符时不拼 |
| 「命令退出即结束会话」 | 支持（用 `exec` 包装） | 支持 | **不支持**（没有 `exec`；表单里置灰并说明，已勾选的会被撤掉） | 同左 |
| 守护唤醒时在命令后追加提示词 | 支持（POSIX 单引号） | 支持 | 不追加，提示词另行发送 | 同左 |
| 非交互续聊预设 | 支持 | 支持（见下面的 PATH 说明） | 暂不支持（表单里提前说明） | 同左 |

**验证到什么程度**

- Linux：全部有端到端覆盖（`terminal-launcher`、`terminal-guard`、`launcher-run`、`guard-headless`）。
- PowerShell 的写法：在 PowerShell 7（Linux 版，放进 PTY 当交互式会话，与 Agent 起的会话 shell 等价）上实测——目录名含空格、引号、弯引号、`$`、反引号、方括号、`&`、`;`、`#`、中文都能进入；目录不存在时，同一行里后面的命令不会运行。
- 浏览器侧的表单与启动流程：真实浏览器里用「改写主机列表」的办法扮演 Windows / macOS 主机（`launcher-platform`），验证表单怎么展示、点「启动」敲进终端的是哪种写法。
- **Windows 实机（2026-10-18，经 ExecMesh 在一台 Windows 主机上，Windows PowerShell 5.1.26100；脚本见 `scripts/e2e-terminal/winhost/`）**：用真正的 `startLine` 输出逐条运行，PowerShell 22 条、cmd 19 条，共 41 条全部通过——目录名含空格、`'`、四种弯引号、`$(…)`、`$HOME`、`;`、`&`、反引号、`#`、`@`、`%`（仅 PowerShell）、方括号、中文，以及 `~` 的三种写法（`~`、`~\x`、`~/x`）都进了正确的目录；判定**既看 shell 自己的当前位置，也看命令里再起的原生子进程实际拿到的工作目录**（`claude` / `codex` 这类原生程序拿到的是后者）。目录不存在时整行中止、命令不运行（PowerShell 退出码 1；cmd 里 `&&` 短路，退出码 1）；Windows PowerShell 5.1 里写 `&&` 是语法错误（所以启动行用分号）；逐行输入时，坏目录那一行失败、下一行照常运行。测试只在 `%TEMP%` 下建了一个专属目录并在同一条命令里删除，事后复查没有残留。
- 实测时见到 PowerShell 自身的一个怪癖（与启动器无关）：新起的 `powershell.exe` 如果工作目录名里含 `[` `]`，它自己的「当前位置」会和进程工作目录对不上（原生程序拿到的仍是对的）。启动器总是再发一句 `Set-Location -LiteralPath`，所以会话本身不受影响；只有「命令本身又是一个新开的 PowerShell」且目录名含方括号时才会遇到。
- 启动耗时：该主机上 `powershell.exe` 从启动到退出约 0.2 秒（5 次，冷热无差别），远小于浏览器「静默 350 毫秒 / 最多等 4 秒」的就绪判断；这不含 ConPTY 与 PSReadLine 的加载，真实交互会话里提示符会稍晚出现。
- **仍需要实机确认**：ConPTY 里真实交互会话的提示符时序（上面只量了进程启动）、macOS 的 zsh 与 PATH、Cursor CLI 在 Windows 上的命令名与安装位置。

**已知限制与建议**

- 旧版会话守护进程不上报 shell 与家目录（升级 Agent 即可）：Windows 主机上不拼「进入目录」那一句，目录不存在时会静默回落到默认目录，表单会提醒。
- macOS 上非交互续聊用 `bash -l -c` 运行，bash 只读 `.bash_profile` / `.profile`、不读 `.zshrc`：命令找不到时，在预设的「可执行文件」里写完整路径（例如 `~/.local/bin/agent`）。
- 在 Windows 上先用「终端」预设、不带目录试一次 `agent --version`，确认命令名与 PATH，再加目录与守护。

### 8.11 待接入会话的「启用 Agent」：无人值守地新开对话（#176 第 3 阶段）

网页上新建的会话在智能体接入之前是「待接入」。以前只能把「启动提示词」复制给某个智能体，由它第一次调用 RelayMesh 时接进来。现在会话页输入区的快捷条里有一个「**启用 Agent**」：在某台主机的某个目录里**无人值守地新开一个 Cursor CLI 对话**（`agent -p …`，不带 `--resume`），它按提示词带着这个会话的工作流编号接入 RelayMesh，之后这个会话就和别的智能体会话一样了（状态卡、§8.9 的「运行」按钮、预设……）。

- **新建时的高级选项（#184）**：侧栏底部的「新建会话」弹窗里，名字仍是唯一必填项；名字下面有一个默认收起的「**高级选项**」，展开后可以再填五项（全是可选的，不填就和以前完全一样）：**工作流编号**（自己指定，字母或数字开头、可含 `.` `_` `-`，3～64 个字符，已存在会提示撞号；不填自动生成）、**首条指令**（智能体接入前先写好，进收件箱，接入后第一次调用就读到；最长 20000 字）、**起始阶段**（讨论 / 方案 / 开发，不选保持默认）、**项目目录**（绝对路径）与**主机**（会话的归属标签）。建好后第二步会把这些设置逐项列出来；首条指令或阶段没设上时（会话本身一定已经建好）用琥珀色写明哪一项为什么没成、怎么补。接口是同一个 `POST /api/v1/workflows`，请求体多了可选字段 `workflow_id`、`first_message`、`phase`、`project_directory`、`host_name`，响应多了 `applied` 与 `warnings`（没有时不出现）；旧前端只传 `title` 照常可用。**填了项目目录 = 这个工作流从此绑定该目录**：智能体第一次汇报带的 `project_directory` 与它不一致会被项目所有权校验（D-161）拒绝，所以启动提示词会要求智能体原样回填这个目录；它同时成了这个目录里最近更新的工作流，所以之后该目录里**没带工作流编号**的汇报（按目录继承最近的工作流）会被并进来，带了编号的、别的目录的都不受影响（`TestCreateWebWorkflow_BoundDirectoryJoinsDirectoryInheritance` 钉住了这个口径）；没有「解除绑定」的入口，想换目录就新建会话。
- **入口**：终端子系统开着、Hub 认识这个功能、并且这个会话现在是「待接入」（会话行全是网页新建的 `sess-web-` 占位，与页头状态徽标同一口径）时才出现；一旦有智能体接入，按钮自己消失、换成「运行」。点开是一个弹窗：主机（只有一台在线、或只有一台主机时自动选中）、目录（主机上的绝对路径，作为 `--workspace`）、模型（可选）、权限姿态、最长运行时间、异常退出时自动续跑、「高级」（可执行文件、提示词），下方是一句话总结与「将运行的命令」（可展开，整行命令可核对）。选项有错时点「启用并运行」只亮出错误，不会发到主机。
- **默认值**（你在 Q43 里定的）：权限姿态默认**放开全部命令**（`--force`），弹窗里有红字警告——无人值守的智能体可以不经询问地在这台主机上运行任何命令、改任何文件，只在完全信任这个目录与这台主机时使用，想收紧就改选「只放行白名单内的操作」；最长运行 24 小时；自动续跑关闭。**接口本身的默认是安全的**（权限姿态不填 = 白名单，最长运行不填 = 平台上限 7 天），放宽只发生在弹窗里并且是明示的。弹窗会记住上一次的主机、目录、模型与可执行文件（存在浏览器本地），下次预填；权限姿态与最长运行时间不记，每次都从上面的默认值开始，不会因为上次放开过就悄悄沿用。
- **点「启用并运行」**（需要刚刚解锁，和新建、修改、运行预设一样）一次做两件事：创建（或复用）一条非交互续聊预设，再运行它。预设由工作流编号派生（编号 `ea-<工作流编号哈希前 16 位>`、名字「启用 Agent · <会话名前 16 字> · <工作流编号末 6 位>」），**每个工作流只有一条**，再次启用时复用并按弹窗里的新选项更新；运行失败就撤掉刚为这次运行新建的预设，不留半成品。预设带 `run.new_conversation: true` 与 `run.origin: "enable_agent"`，启动器里显示「由「启用 Agent」创建」，编辑保存后标记仍在。预设已满 20 条时拒绝（`launcher_limit`）。所以它走的是 §8.7 的同一条通道、同一套闸门（总闸、暂停、主机的模型访问、执行模式——需批准的主机上先停在待批准、令牌限额）、同一个命令拼装器，不另开旁路。
- **命令**：`<可执行文件> -p --approve-mcps --trust [--model <模型>] [--force] --workspace '<目录>' --output-format stream-json '<提示词>'`，**没有 `--resume`**。默认提示词告诉智能体：这是一次无人值守的新对话，没有人看终端输出，结果必须发到 RelayMesh；先调用 `interactive_feedback` 汇报一次（异步模式用 `wait:false`），参数里必须带这个 `workflow_id` 与你当前工作区的绝对路径；第一条指令可能在回执或收件箱里；之后的汇报都沿用同一个 `workflow_id`；「等我回复」在这里等于结束本次运行；权限以回执 `auth` 行为准。「高级」里可以改提示词（`%workflow` 换成工作流编号），也会补上本次的最长运行时间。
- **对话编号怎么学到**：新开的对话一开始没有编号，Hub 从这次运行输出里 `system/init` 事件的 `session_id` 学到它，记成这个工作流的对话编号，聊天里写一行系统行「新对话已建立（对话 xxxxxxxx…）：之后的运行都会接着它，不会再新开」。从此这条预设的每次运行（手动运行、自动续跑、会话页「运行」）都是 `--resume <学到的对话>`——**新开只发生一次**。Hub 重启后仍在进行的运行会被接回，已学到的编号照常恢复，不会重复记这一行。
- **对话归谁（认领，#182）**：Hub 发起的运行清楚自己替哪个工作流跑、跑的是哪个对话，所以运行一旦读到输出（新开的对话就是读到 `init`）就**认领这个对话**：对话的状态会话、旧链路里的对话编号与活动时间、hook 的收件箱轮询，都归发起运行的工作流。这是因为 hook 汇报带的工作流来自项目目录里的 `.cursor/relaymesh.json`，**同一个仓库的多个 git 工作树共用一份被提交的配置**时，它写的常常是别的工作流——不认领的话，新对话的会话会被建到那个工作流名下、运行读到的对话没人认回来、之后 hook 的汇报又被运行权威挡掉没人纠正，表现就是「启用后会话页没有这个对话的状态、「运行」按钮也找不到预设」，别的工作流名下还多出一个幽灵会话（还可能让它自己的预设去续聊这个对话）。认领会把已经建在别处的会话与旧链路搬回来，并通知两边的网页刷新；认领与运行权威同生共死（运行读到输出才认领、每轮续期、运行收尾的几秒后失效），启动就失败的运行不碰对话；Hub 重启后接回运行时重新认领，已经卡在错误工作流里的会话会自己归位。会话页「运行」找预设时，工作流还没有智能体状态会话（hook 没汇报过）就用工作流上记录的主机与目录，不再一口咬定「会话没有上报项目目录」。想从根上避免，仍建议各工作树各自生成并忽略 `.cursor/relaymesh.json`（见收件箱文档的 hook 配置一节）。
- **防重复**（不会开出两个智能体）：这个工作流已经有智能体在运行 → `conversation_live`；上一次运行还没结束 → `run_active`（另有同一预设的进程内互斥，快速双击也只会跑一次）；已经学到对话编号 → 不再新开、改为接着它运行；已经不是「待接入」→ `not_pending`（409，「请用会话页的「运行」接着它」）。弹窗里的预览实时写出这些原因并把「启用并运行」置灰，点击提交之后按钮立刻置灰并写「启用中…」。
- **绑定了项目目录的会话（#184）**：会话在网页新建时若绑定了项目目录（见上面的「高级选项」），智能体第一次汇报带的 `project_directory` 必须与它一致，所以「启用 Agent」没填运行目录时**默认用绑定的目录**——弹窗里只要你没亲手改过目录框（或把它清空），目录就是绑定目录，盖过「上一次记住的」目录，目录框下面写明「这个会话在网页里绑定了项目目录 …」。亲手填了别的目录时，预览报 `dir_mismatch`（409，「启用并运行」置灰，提交被拒绝，不建预设、不到达主机；命令预览仍然显示，方便核对）——否则要等智能体起来、第一次汇报被拒绝之后才会发现。比较口径与项目所有权校验一致（去首尾空白后 `filepath.Clean`，`/work/app/` 与 `/work/app` 算同一个）。没绑定目录的会话与以前完全一样；预览多一个只读字段 `bound_dir`（没绑定时不出现）。
- **范围与拒绝原因**：只支持 Linux / macOS 主机；Windows 主机拒绝（`unsupported_os`，提示等「开终端启动」那一期，即第 2 阶段，2.0 之后做）。其余拒绝码：`no_workflow`、`workflow_not_found`、`no_host`（多台主机又没选）、`host_offline` / `host_not_found`、`no_dir` / `bad_dir`、`dir_mismatch`（运行目录与会话绑定的项目目录不一致）、`bad_options`（选项不合法）、`launcher_limit`，以及继承自预设运行的闸门类原因（总闸、暂停、模型访问被拒……）。
- **不扩大智能体的权力**：只在人点了「启用并运行」时发生；**MCP 没有新增工具**，智能体不能经 MCP 启用别的智能体。
- **接口**：`POST /api/v1/terminal/session-enable/preview`（登录即可，只读，不产生任何记录，返回 `{preview}`：待接入与否、绑定的项目目录（`bound_dir`，没绑定时没有）、候选主机、生效的选项、将运行的命令、警告、拒绝原因、已有的预设与它最近一次运行）；`POST /api/v1/terminal/session-enable`（需解锁，成功返回 `{run, preset:{id,name}, prefs}`，被拒时 `{code, error}`）。请求体字段：`workflow_id`、`host`、`dir`、`bin`、`model`、`posture`、`conversation_id`（可选，给了就接着这个已有的 Cursor 对话、把它接到这个会话上）、`prompt`、`max_run_minutes`、`auto_resume`。
- **审计**：`session_enable`，只记 `workflow=… preset=… posture=… new=…`，不含提示词与命令。
- **回滚兼容**：没有新增表或列。预设 JSON 里多了 `run.new_conversation` 与 `run.origin` 两个可选字段，旧版本忽略它们——这类预设在旧版里没有可用的对话编号，不要在旧版里重新保存；旧版没有 `session-enable` 接口（404），入口自然不出现；学到的对话编号存在原有的智能体链接里，旧版照常读。
- **测试**：`internal/terminal/{session_enable,launcher_newconv,run_claim}_test.go`、`internal/store/{terminal_launcher_run,agent_claim}_test.go`、`internal/mcp/agent_claim_test.go`、`frontend/src/lib/terminal/sessionEnable.test.ts`；浏览器 e2e `scripts/e2e-terminal/e2e/enable-agent.mjs`（15 步：入口只在待接入会话上出现、默认值与红字警告、校验不过不到达主机、命令里没有 `--resume`、解锁、防重复、学到对话编号后再运行是 `--resume`、已接入的会话被拒、白名单选项带进命令、启动器里的来源标记、审计、窄屏、hook 配置写着别的工作流时的对话认领、绑定了项目目录的会话默认用绑定目录且改成别的目录被拒；预设里的命令必须是假 agent 的绝对路径，脚本里有安全闸，实验 Agent 的 PATH 里也没有真实 Cursor CLI）。

### 8.12 项目管理 Agent 运行预设（MCP 工具 `preset_run`，#179）

总控 Agent 想让某个子会话接着干活，以前只能由你在网页上点那个预设的「运行」。现在，项目的**管理 Agent**可以经 MCP 工具 `preset_run` 运行**本项目里已有的**「非交互续聊」预设（§8.7）：它只负责「按下运行」，主机、目录、对话、模型、权限姿态与提示词都是你事先在预设里定好的，它改不了，也看不到命令与提示词。

- **默认关闭，要同时过两道闸**：
  1. **令牌带「运行预设」权限**（设置 → MCP 与安全 → 凭据权限里一行琥珀色的选项；默认不勾，也不在「全选」里）。没勾时 `preset_run` **根本不出现在 `tools/list` 里**，硬调用也被拒绝。授予它和授予终端权限一样要**重新输入密码解锁**，收紧（取消勾选）只要登录。它必须和治理类工具（沟通反馈、会话查询等）一起开；令牌强度要够（与终端权限同一条弱令牌规则：创建、修改时拒绝，运行时再查一次）；**能力 URL 凭据（令牌就写在链接里）不能带这一项**。
  2. **调用方是项目管理 Agent**：你在项目页「任务管理」里勾选了它（持有任务管理授权）。这一条**与项目的权限档位（关闭 / 审计 / 强制执行）无关**，档位关着也照样检查——运行预设不是读写项目内容，而是让别的会话开始干活，不能因为没开强制执行就放开。
- **能运行哪些预设**：「非交互续聊」预设里，目标工作流（`run.workflow_id`）在**这位管理 Agent 所在项目的任务板上**、并且**不是它自己的工作流**的那些。别的项目的预设、没配工作流的预设，和「根本没有这个预设」是同一个回答（`preset_not_found`），不泄露别的项目里有什么；它自己的工作流是 `own_workflow`（避免自己唤醒自己）。
- **三个动作**：`list`（能运行哪些预设：编号、名字、目标工作流、主机显示名、权限姿态、模型、最长运行时间、现在能不能运行及原因、最近一次运行的状态与最后一条回复）、`status`（单个预设的同样信息）、`run`（运行一次，返回运行编号与状态；运行有没有结束再用 `status` 查）。参数只有 `action`、`preset`（编号或名字）和用来认出自己的 `workflow_id`（`project_directory`、`host_name` 可选）。**没有提示词、命令、目录、对话编号、模型、权限姿态这些参数**，夹带的多余字段被忽略，也不会出现在返回里。回执里附带当前生效的频率护栏数字，方便它自己安排节奏。
- **走的是网页上点「运行」的同一条路径**：总闸、暂停、主机的「模型访问」、主机执行模式（「需批准」的主机上停在待批准）、令牌限额、预设单飞（`run_active`）、「对话还在运行」（`conversation_live`）一个不少，没有旁路；运行本身与 §8.7 完全一样，只是多了一层频率账本。
- **频率护栏**（代码常量，写在工具说明与拒绝信息里）：同一个管理 Agent 同时最多 **3** 条自己发起的运行在进行（`agent_run_concurrency`）；每小时最多 **10** 次（`agent_run_hourly`）；同一预设两次由 Agent 发起的运行之间至少隔 **5 分钟**（`agent_run_preset_gap`）；所有 Agent 合计 24 小时最多 **30** 次（`agent_run_daily_cap`，两个管理 Agent 互相唤醒形成循环时由它拦住）。账本读终端审计里**成功提交**的记录（回看 7 天），所以 Hub 重启不会清零；检查与提交在同一把锁里，并发调用不会一起越过上限。检查顺序是当天上限 → 预设间隔 → 并发 → 每小时。被拒绝的调用不占名额。
- **留痕，且都不含提示词、命令与令牌**：终端审计 `launcher_agent_run`（成功 / 拒绝 / 失败，记预设编号、工作流、权限姿态与发起的身份；拒绝记录自带每分钟上限，刷不满日志）；项目审计 `launcher.run`（范围「任务」，放行 / 拒绝，审计页里显示「运行预设」，展开有白话原因；同一条拒绝原因 30 分钟内重复只记一条，不同原因各记各的）；聊天里一行系统行「项目管理 Agent「X」运行了预设「Y」（非交互续聊 · 接着对话 … · 模型 · 权限）」；运行记录的说明末尾带「（项目管理 Agent「X」发起）」，预设清单的运行卡片据此显示发起者。
- **身份是自报的，所以真正的控制是「令牌权限位 + 频率护栏」**：管理 Agent 的身份由调用里的 `workflow_id` 加它汇报过的目录认出来（凭据 + 主机 + 目录），没有额外的密码学证明——拿到这把令牌的人可以冒用同一令牌下任意已汇报的身份。所以请只把「运行预设」权限给你信任的那一把令牌；它能做的上限是：运行本项目里你已经定好的预设，次数受护栏限制，每一次都有记录。
- **第一次真实运行请你在场**：已用假 agent 在实验 Hub 上端到端验证（见下），**还没有在真实主机上用真实 Cursor CLI 运行过**；第一次真实运行后请看一眼运行记录、状态卡与聊天里的系统行。
- **回滚兼容**：没有新增表或列。凭据权限里多了一个可选的 `launcher` 布尔字段（没开时不出现）：旧版本忽略它，这把令牌在旧版里等于没有这项权限，工具不存在；旧版里重新保存这把凭据会丢掉它（只会更保守）。审计里新增的 `launcher_agent_run` / `launcher.run` 事件，旧版只是当作不认识的类型显示原始值。
- **测试**：单元测试 `internal/terminal/agent_run_test.go`（资格、账本、护栏次序与重启不清零）、`internal/mcp/tools_preset_run_test.go`（工具可见性、闸门、忽略夹带参数、弱令牌）、`internal/api/credentials_launcher_test.go` 与 `internal/model/permissions_launcher_test.go`（权限位与解锁）、`internal/store/projects_test.go`（审计去重）、`frontend/src/lib/{credentialPolicy,projects}.test.ts`；浏览器 e2e `scripts/e2e-terminal/e2e/preset-run.mjs`（15 步：工具可见性、两道闸、列表只含本项目子会话预设、夹带参数被忽略、`run_active`、结束后的状态与聊天系统行、预设间隔与并发护栏、自己与别的项目的预设、审计与日志不含提示词和命令、权限页与项目页与审计页的界面、收紧与解锁、能力 URL 与弱令牌的创建限制；预设里的命令必须是假 agent 的绝对路径，脚本里有安全闸，实验 Agent 的 PATH 里也没有真实 Cursor CLI）。

## 9. 终端流量压缩（WebSocket permessage-deflate）

终端的 WebSocket 链路（浏览器 ↔ 服务端、服务端 ↔ Agent）现在协商 `permessage-deflate`（带上下文接管，对 Cursor CLI 这类整屏重绘的输出压缩比约 7:1），任何新旧版本的组合都能正常工作：

| 链路 | 何时生效 |
|---|---|
| 浏览器 ↔ 服务端 | 服务端升级后立即生效，不需要升级 Agent |
| 服务端 ↔ Agent | 要**Agent 升级后**才压缩；旧 Agent 仍按未压缩工作 |

打开终端时的卡顿还和「终端尺寸变化会让 Cursor CLI 把整段对话重画一遍」有关：页面现在在第一次适配尺寸之前就装好渲染器，并把尺寸上报防抖到 400 毫秒，所以打开同一个会话、拖动窗口触发的重画次数都明显减少；已结束会话的「查看记录」与运行中的一样，只载入最近约 3 MiB 窗口、停在末尾，向上翻时再按需读取。

## 10. 输出太快、浏览器跟不上时的「追赶」保护（#101）

Cursor CLI 这类内联界面在**终端尺寸变化**（打开会话时窗口尺寸与会话不一致、拖动窗口、别的设备附着后改了尺寸）或自身重绘时，会把整段对话再打印一遍，单次可达几十 MiB。主机与浏览器之间是**无损背压**：浏览器或链路慢多少，输出就被「配速」多少——不丢内容，但这一整段会以链路速度一路滚过屏幕，慢链路上要滚几秒到几十秒。

现在的行为：

- **打开即最新**：打开一个运行中的会话，主机只回放末尾约 20 屏，回放渲染完之前终端上盖一层「正在载入最新内容…」遮罩（带进度），渲染完直接落在最新屏幕；回放渲染完后若输出还在高速涌来（典型：尺寸变化引起的整段重画），遮罩会继续盖到输出平静（最多 3 秒）。安静的会话没有额外等待。
- **跟不上就跳到最新**：会话**开着记录**（默认）、而浏览器持续跟不上输出（在途数据持续接近窗口上限，约 0.5 秒后遮罩显示「输出太快，正在跳到最新输出…」，约 1.2 秒后）时，服务端断开这条附着（关闭码 `4414`、审计 `lagging`）；浏览器稍候（1.5 秒起，连续被断开时逐次加倍，最长 6 秒）后**重新附着，只回放末尾并清屏重建**。被跳过的中间内容没有丢，在会话记录里，滚到顶或用右上角「历史日志」可以读到。
- **不会挡住你按 Ctrl+C**：你刚敲过键的 2 秒内服务端不断开；断开重连的空档里敲下的最后几个按键（≤ 512 字节）由浏览器暂存、重连后按序补发。
- **后台标签不再被拖垮**：不在前台的窗格被这样断开后不自动重连，再被看到时才重新附着。
- **没有记录的会话（无痕 / 记录异常）不适用**：被跳过的内容无法找回，所以保持原来的无损背压，遇到整段重画仍会慢慢滚。
- **兼容**：只需要升级服务端（浏览器代码随服务端内嵌）；旧 Agent、旧会话守护进程照常工作；新帧 `lag` 与关闭码 `4414` 对旧版浏览器无害。

**遇到「忽然滚屏」想让我们查原因时**：在终端上点右键 →「复制连接诊断」，把复制出的文字发过来。内容只有连接 / 就绪 / 关闭 / 重试 / 尺寸上报 / 遮罩 / 历史载入这些事件的相对时间与简单数值，**不含终端内容，也不含完整会话 ID**；有了它才能判断触发源是尺寸变化、程序自己重画，还是多个设备互相改尺寸。
