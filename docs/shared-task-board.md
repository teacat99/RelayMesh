# 共享任务板

任务板把「要做的事」从会话里拆出来，像工作表一样独立保存，并按项目（工作流）组织。智能体用 `task_board` 工具维护它，用户在 Web 的任务页实时看到同一份清单。一个项目里的多个工作流共用同一张板和同一套 `#编号`。

## 什么时候用任务板

- 工作有大约 3 步以上、会跨会话或跨上下文重置、或者用户希望被追踪时，先建任务再动手。
- 一两步就能做完的小事不用建。
- 每次开工、上下文被重置之后，先调用一次 `task_board`（默认动作 `overview`）：清单是空的，它直接告诉你下一步怎么建；已有清单，它给出模块规划树、各状态数量、正在做和验证中的任务、维护守则和需要整理的地方。
- 任务记录「做到哪了」，设计依据和推理放在项目文档库里（见 `project-docs` 主题），两者配合使用。

## 数据模型：模块规划树 + 任务

- **模块 → 功能**两级规划树：模块是项目里稳定的功能域或子系统，功能是模块里的具体能力，例如模块「终端」下有功能「终端/历史日志」。
- **模块名是封闭名单**：任务只能标注已有的模块路径，各会话的标注不会各写各的；要新模块或新功能，先用 `plan` 声明（报错信息会列出现有路径）。
- **任务**挂在模块路径下，编号 `#12`；没有模块的任务归在「未归类」，要尽快清零。
- 汇报、提问、任务描述里写 `#12`，Web 会自动变成可点击的链接。

## 第一次使用：规划模块

清单还是空的时候，先看项目自己的结构（目录、README、设计文档），再用 `plan` 一次定义 3 到 8 个模块（可带功能）：

- 模块 = 项目里稳定的功能域或子系统，外加 2 到 3 条横切的工作线，例如「发布与运维」「质量与测试」「文档与待办」。
- **不要**按「第 N 轮 / 第 N 批」、日期、会话、负责人或工作阶段（评估、开发、测试）划分，也**不要**建「其他」「杂项」「misc」这类兜底桶——这些名字几周后就失去意义，清单会变成流水账。
- 限制：最多两级，一个模块最多 30 个功能，模块名一行、不超过 40 个字符，说明不超过 200 个字符，名字里不能带 `/`。

## 日常维护

- 新任务先在已有路径里找归属，`module` 写完整路径；确实没有合适的功能，才用 `plan` 追加一个功能（新增顶层模块应当很少见，更不要一次对话建一个）。
- 一个交付物就是一个任务，它自己沿着状态和阶段往前走：不要为评估、方案、开发各建一个任务，也不要建一个「本轮」父任务去打包用户这次提的几件事（`parent_task_id` 只用于真正分成多块的同一件交付）。用户一次提了几件事，就各归各的功能域。
- 创建任务时写 `description`（这是什么、做到什么算完成，一小段话；标题只是名字）。
- 用 `batch` 一次创建多个任务、成批更新状态和进度（`task_ids` 可以对多个任务套同一个改动），不要一个一个地调用。同一个模块里已有同名的未完成任务时，`batch` 会复用它而不是重复创建。

### 任务状态

状态是 `todo`（待办）→ `doing`（进行中）→ `review`（验证中）→ `done`（已完成），`shelved`（暂缓）是旁支。它绑定的是智能体自己的开发流程：

- `review` = 开发完成，正在跑回归、相关测试、部署后的冒烟。
- `done` = 验证通过并已交付，由智能体**直接置为已完成并同时写下结论**（做了什么、怎么验证的）；没写结论的完成会被服务端拒绝，新建任务也不能直接是 `done`。
- 已完成的任务，发现问题可以重新打开，时间线会记明是谁做的。
- 不再有需要用户逐条点头的「待确认」环节：用户随时可以手动改任何状态，验收后发现问题，就在任务上「发起改进需求」。
- 用户回复以「改进需求 #N「标题」：……」开头，表示他在这个任务上发起了改进：任务已被置回进行中（阶段「改进」），不要另建新任务，读完任务的描述和时间线，改完、验证通过后照常置为 `done`。
- 异步对话模式下，必须等用户拍板才能继续的任务，先发确认卡（`async_ask`）再置为 `shelved`，并在进展里写明在等哪张卡（`Q<N>`）；暂缓的任务不算「在做」，不挡回复窗口，也不挡收尾（见 `async-mode` 主题）。
- **严格收尾门**（异步会话默认开）按指派关系判定「谁的任务挡谁的收尾」：没有指派的归创建者；已指派的待办 / 进行中归承接者；承接者拒绝的待办回到派发者；协作指派、承接者已交付待验收的验证中归派发者；你在网页上派的任务、已交付待验收或被拒绝时没有智能体要处理，不挡任何会话。同一个任务任一时刻只挡一方，所以不会两个会话互相等对方（详见 `async-mode` 主题的「严格收尾门」）。

### 阶段、进度与完成度

- **阶段**（`stage`）：`assess`（评估）→ `plan`（方案）→ `dev`（开发）→ `improve`（改进），说明任务此刻在做哪一类工作。它和状态、类型都无关，Web 任务页把它画成第二条进度条，不确定就不填。注意它和会话的「讨论 / 方案 / 开发」阶段不是一回事。
- **进度**（`progress`）是覆盖式的「现在做到哪、下一步做什么」，不超过 500 个字符，不是流水账。
- **完成度**（`percent`）0 到 100，只在能给出可信数字时才填，传 `-1` 清除；没填的按子任务比例或状态推导。
- **结论**（`conclusion`）1 到 3 行，不超过 400 个字符，任务到达 `review`、`done` 或 `shelved` 时写。
- 类型 `kind`：`bug`、`feature`、`improve`、`research`、`ops`。

## 工具与动作

`task_board` 有四个动作：

| 动作 | 用途 |
|---|---|
| `overview`（默认） | 整张板一眼看完：各状态数量、模块树（未完成 / 已完成 / 总数 / 完成度）、进行中与验证中的任务、几条待办、分配给你与等你验收的任务；板是空的时给出用法 |
| `list` | 按条件列任务：`module`、`states`（默认待办 / 进行中 / 验证中）、`include_closed`、`kind`、`query`、`assignee`（`me` / `none` / 某个工作流）、`sort`（`plan` 按模块树顺序，`recent` 最近进展在前）、`limit`（默认 30，最大 100） |
| `plan` | 一次声明整棵模块树：幂等（重复发送同一份计划不改变任何东西）且原子（一个节点非法则整体不生效）；新节点追加在末尾，`reorder` 为真时按你给的顺序排；`remove` 只能删除没有任务也没有功能的节点 |
| `batch` | 一次创建或更新最多 30 个任务；带 `modules` 时先应用规划，所以「规划 + 全部建任务」可以是一次调用；每个任务单独返回结果，一个失败不影响其他 |

此外，`workflow_context` 提供单个任务的 `task_create`、`task_update`、`task_get`、`task_list`，同样支持 `module` 与 `percent`。长度上限：标题 200、描述 1000、进度 500、备注 500、结论 400 个字符。

服务端还会做轻量的「结构体检」：模块名带着轮次、日期或阶段的痕迹，或者是「其他 / 杂项」，顶层模块过多，有未归类任务时，`overview`、`plan`、`batch` 的回执和回执头里的 `tasks` 行都会提醒你整理（只提醒，不拒绝）。

## 共享任务板：一个项目的多个工作流协作

同一个项目里的工作流共用这张板和它的 `#编号`。有两种角色：

- **管理 Agent**：用户在项目页勾选出来的智能体（见 `projects-and-access` 主题），以及用户本人。默认没有任何管理 Agent。
- **普通智能体**：只能写自己的任务（自己创建的，或分配给自己的），其他任务只能读。

### 派任务与承接

1. **派任务**：管理 Agent 或用户用 `batch` 里的 `assignee=<工作流编号>` 把任务交给同一个项目的另一个工作流；`assignee` 传空字符串表示撤回。派任务时每次至少交出 2 个任务，把工作拆成最小的独立块，只有确实不足两块时才少交。
2. **承接**：被派的工作流在 `overview` 的 `assigned_to_you` 里找到任务（或用 `list` 加 `assignee=me`），用 `claim=accept` 接下（`todo` → `doing`），或用 `claim=decline` 拒绝并在 `note` 里写原因。
3. **推进**：承接者照常更新 `progress`、`percent`、`note`。
4. **交付**：做完用 `claim=deliver`（状态 → `review`；`note`、`progress`、`conclusion` 写清做了什么、怎么验证的）。
5. **验收**：被派的任务**不由承接者自己完成**。派任务的人（或管理 Agent、用户）用 `claim=accept_delivery` 验收（状态 → `done`，必须写 `conclusion`），或用 `claim=reject_delivery` 打回（`note` 写原因）。等你验收的任务列在 `overview` 的 `awaiting_your_acceptance` 里。

几点补充：

- 自己把被派任务的状态置为 `doing` 或 `review`，等同于接下或交付。
- `claim` 只能用在已分配的任务上，不能和 `assignee` 同时出现在同一个操作里。
- 只有管理 Agent 或用户能分配任务。唯一带范围的例外是分支会话：主会话的智能体可以把**自己创建的任务**派给**自己的、用户开放了「任务」派单的活动分支**，分支接取、交付后由主会话验收（见 `branch-sessions` 主题的「主会话给分支派任务」）；其余规则不变。

### 回执头里的待办提醒

不必记着去翻 `overview`：只要有协作的事在等你处理，每次工具回执的头部（`tasks` 行之后）都会多一行 `board:`，处理掉它就消失；没有待办时这一行不出现。

| 提醒 | 谁会看到 | 怎么处理 |
| --- | --- | --- |
| 指派待你接取 | 承接者 | `claim=accept` 接取，或 `claim=decline` 并在 `note` 里写原因 |
| 交付被退回 | 承接者 | 看任务时间线上的退回原因，改完再 `claim=deliver` |
| 已交付待验收 | 派任务的人 | `claim=accept_delivery` 验收，或 `claim=reject_delivery` 退回 |
| 指派被拒绝 | 派任务的人 | 看拒绝理由，改派给别人或自己做 |
| 超过 2 小时没人接 / 承接者已不存在 | 派任务的人 | 催一下对方，或改派 |

每一类最多列 5 个编号；「待接取」和「没人接」还会写出最久已等多久。「超过 2 小时」是默认的阈值，可以在 设置 → 外观与通知 →「指派久无人接的提醒」里改成 30 分钟 ~ 24 小时（回执里就会写成你设的时长，比如「超过 4 小时没人接」）；下面网页上「已等」什么时候标红、「久无人接」的提醒用的是同一个数。自己派给自己的任务不算协作，不会出现在这里；已完成和已搁置的任务也不再提醒。

### 网页上的提醒

智能体靠回执头知道自己手上有活没接，人在网页上也能一眼看出「谁手上有指派没接、等了多久」：

- **侧栏会话卡的徽标**：某个工作流手上有被派来、还没接取的协作任务时，它的会话卡右下角出现琥珀色的「N 项待接取」，悬停写明「最久已等多久」。接取、拒绝、撤销后徽标实时变化，不用刷新；没有待接取的指派时卡片与以前一样。
- **任务页的快捷项**：板上出现过指派后，筛选栏里多出「指派给我 / 我派出的 / 待接取」三个快捷项，数字是还没结束的任务数。「我」就是任务页正在看的那个工作流；用户在网页上派的任务算「指派给我」，自己派给自己的两边都不算；再点一次取消，选中的快捷项没有任务了会自动取消。
- **行上的「已等多久」**：待接取的任务在承接者标记后面写「刚派出」或「已等 3 小时 20 分」，超过阈值（默认 2 小时，见下）变红，悬停写「指派超过 N 小时还没人接」，提醒派任务的人去催或改派。
- **「指派久无人接」的提醒（给你一次）**：指派派出后一直停在「待接取」超过阈值，系统会提醒你**一次**——浏览器里弹一条系统通知（按你的通知设置，也可以响提示音），例如「#12「接口改造」派给 后端组，已超过 2 小时没人接」。同一个承接者名下同时到点的多个指派合成一条（「3 个指派（#12 #13 #14）派给 后端组……」），一次最多发 5 条，剩下的下一轮再发。点开提醒：只有一个指派就直接打开它的详情；有多个就打开承接者的任务页并套上「待接取」筛选（原来的搜索词与别的筛选会被清掉，免得提醒指的东西被旧筛选藏住）。
  - **每个指派只提醒一次**：提醒过的会记在任务上，重启不会重复；被拒绝或撤销后重新派出，算新的一轮，到点后会再提醒一次。这个标记不改动任务本身——任务的更新时间、时间线、清单缓存都不受影响。
  - **开关与阈值**：设置 → 外观与通知里的「指派久无人接的提醒」有一个开关和一个时长（30 分钟 ~ 24 小时，默认 2 小时；选「默认」就是跟着系统默认走）。开关只管提醒，不影响任务行标红与回执头——这两处只看时长。时长一改，回执头、行上的标红和提醒立刻按新的数走。
  - **关着开关或开着免打扰时不提醒，也不丢**：这两种情况下到点的指派不会被标记成「已提醒」，等开关打开、免打扰结束后的下一轮扫描会补发一次（等得比阈值的两倍还久时，补发的提醒会写「最久已等 N 小时」）。
  - **手机推送默认不发**：它在「按消息类型设置」的「异常提醒」里有一行，默认「不推送」，建议 3 级；要手机上也收到，就在那一行选一个优先级。网页里的提醒不受这一行影响。
  - **升级后的第一次**：升级前就已经久无人接的指派，升级后的第一轮扫描会各提醒一次（同样按承接者合成，一轮最多 5 条）。
  - 浏览器里的提醒只会送到打开着 RelayMesh 的浏览器；一个都没开着的时候，这一次提醒不会补发（想不错过，就打开手机推送那一行）。

### 群聊里的系统消息

派任务的人和承接者如果恰好在同一个群里，协作上的几件事会在群里留一条居中的灰色系统消息，群里的人（包括你）不用切到任务页就知道进展：

| 事件 | 群里写什么 |
| --- | --- |
| 派活 / 改派 | `A 把 #12「接口改造」派给了 B` |
| 交付 | `B 交付了 #12「接口改造」，等 A 验收` |
| 拒绝接取 | `B 拒绝接取 #12「接口改造」，等 A 改派` |
| 退回 | `A 把 #12「接口改造」退回给 B 返工`（人在网页上退回时，主语是「你」） |
| 验收通过 | `A 验收通过了 B 交付的 #12「接口改造」`（人在网页上验收时，主语是「你」） |

- **只在两个人都在的群里发**：派任务的人与承接者都是这个群里还在的成员、群没有归档才发；两人没有共同的群就一条也不发。同时在几个群里，每个群各发一条。
- **接取与撤销指派不发**：接取不需要谁再做什么；撤销指派也没有第二个人要知道。
- **批量合并**：一次 `task_board batch` 里「同一种事件、同一对人」合成一条，写个数与编号，例如 `A 一次派给 B 3 个任务：#12 #13 #14`；多于 8 个只列前 8 个。单个任务才带标题。
- **同一件事只发一次**：只有任务的协作状态真的变化才算事件。已经在验证中的任务再交付一次、已完成的任务再验收一次、对同一个人重复指派，都不会再写一条。
- **不打扰任何人**：这些是系统消息，不带 @、不进任何人的收件箱、不算未读，也不影响群里「Agent 互相 @ 的回复链与冷却」的判断；`chat read` 读到的也是换好名字的整句话。
- **人派的、自己派给自己的不发**：用户在网页上派的任务没有派发者工作流，不写；派给自己的任务没有第二个人要知道，也不写。
- **名字跟着群走**：消息里的成员名在读出来时才换成这个群里当前的显示名（和 @、发言人用同一套名字，重名自动加编号），成员改名后旧消息也跟着变。

### 访问控制档位对任务板的影响

- 项目在 `enforce` 档：规则真正生效，只有任务的创建者、承接者和管理 Agent 能改对应的任务。
- 项目在 `audit` 档：规则只记录、不拦截，超出规则的写入照常执行，并在审计里标「强制执行会拒绝」。
- 档位本身的说明见 `projects-and-access` 主题。

## Web 任务页

地址是 `/work/<项目>`；会话页头的「任务」按钮（带「进行中 / 验证中」角标）进入当前项目的任务页，返回按钮和浏览器后退都回到会话。

- 左侧是模块规划树（窄屏收进左侧抽屉）：点节点按模块或功能筛选，「未归类」单独一类。「编辑规划」里可以加模块、加功能、改名、上移下移、删除；删除前会说明后果——里面的任务会变成「未归类」，任务本身不会被删除。
- 右侧任务列表跟随规划树的顺序分组，每个模块里先看正在做的；一批任务（批次）的子任务缩进在父任务下。每一行都有进度条：填了完成度的画实色并带数字，没填的按子任务比例或状态推导、画淡色且不带数字，已完成画满条；分组头显示「已完成 / 总数」与模块进度。也可以切到「最近进展」，不分组平铺，最近动过的排在最前。
- 任务详情显示状态、标题、所属模块、完成度、当前进度、结论和最近 5 条进展；类型、标签、关联会话、来源收进「更多信息」。用户可以手动改任何状态，也可以在任务上「发起改进需求」。
